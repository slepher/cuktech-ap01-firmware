# AP01 独立 App 更新与恢复设计

日期：2026-11-02。状态：设计完成，待分阶段实现与实机验收；本文不是功能已上线的声明。

## 1. 目标与决定

固件作为长期驻留的平台，App 作为可独立交付的业务程序。安装 App 不重新生成或写入完整 ROM；模板发布仍只发布 Bundle。现有设备需要先升级一次支持文件加载、生命周期管理和独立维护的固件，之后兼容 ABI 的 App 更新才不需要刷 ROM。

采用**单一运行 App + 更新期间的临时旧包**。不增加固定 A/B App 槽、不修改原生 ROM 双槽机制。下载和试运行期间保留旧 App，失败允许自动回退；新 App 达到成功判据并持久提交后，允许清理旧包。2026-11-02 用户明确允许临时保留旧 App，这一决定替代此前“停止后直接覆盖唯一 App、失败仅进内置界面”的更新约束；Bundle 的单份完整包约定不变。

本期不做插件市场、多 App 并行、通用 ELF 动态链接器或差分升级。维护与救援不得依赖业务 App、owner/context、稳定槽记录或精确业务 build 匹配。

## 3. 职责与发布边界

| 组件 | 拥有的职责 | 更新方式 |
| --- | --- | --- |
| 固件平台（本仓库） | 原厂菜单/旋钮、Wi-Fi 切网恢复、维护 HTTP 与鉴权验证、系统忙门、App 加载/停止/健康监督、事务日志、回退、内置恢复界面、原生 OTA/切槽 | 完整 ROM OTA；必要时手动恢复 |
| App（codex_status/ports/ap01） | Bridge 配对交互、业务 principal 绑定、C2 通信/重放/回执、Bundle 与模板显示、业务数据和健康回调 | 独立 App 包 |
| Bundle | 模板、字体与声明的数据合同，不含可执行程序 | 现有完整 Bundle 发布 |
| Bridge | 构建产物选择、设备身份核对、上传与原事务查询、真实结果展示 | 桌面程序自身发布 |

本次“大只读响应重放、写回执长度保护”属于 App 业务通信代码：现状必须重新打包并部署含改动的 ROM；新机制实现后可只更新 App。维护协议、加载器、原厂适配或 ABI 服务变更仍需要固件更新。

固件拥有监听器和回调注册表；App 只持有可撤销句柄。App 不在静态固件表中留下函数指针，不直接拥有不可排空的原厂定时器、线程或 UI 回调。固件保存唯一有效代际，停止后业务入口返回结构化 `app_unavailable`，维护入口继续工作。

配对策略和交互属于 App；配对成功后通过受控平台服务建立可撤销的维护授权，凭据由固件持久保存并独立验证。不得在两个仓库复制凭据仓库。授权带 principal、权限和撤销代际；解除绑定必须同步撤销。App 不在线时不能新造授权，也不能把回调失败降级成匿名访问。保留设备侧显式维护授权/原厂救援入口，冷启动无 App 也能使用；实际入口和鉴权实测列入准入证据。

## 4. 执行模型与 ABI

### 4.1 首选实现及硬性可行性门槛

首选“文件包 → 校验 → 加载到固件管理的可执行内存 → 调用稳定 C ABI”。当前固定 ROM XIP 映像不能原样使用。禁止为实现 App 更新直接擦写当前运行 ROM 的 XIP 区。

阶段 S1 必须证明实际 0041 上可执行内存的位置、权限、容量、对齐、缓存同步及中断安全，并用真实业务 App 测量内存和性能。**目前未证明普通堆或 PSRAM 可执行，也未证明完整 App 能装入。** 若失败，停止该执行后端的实施，单独评审文件映射/存储布局替代方案；不得暗中改成固定 App 双槽或削弱 ROM 保护。

优先尝试离线链接的受限位置无关映像。打包器把所需修正规范化为有界的基址/服务地址修正表，设备只接受已经定义的修正类型、目标区间和服务编号，不实现通用 ELF 解析。S1 用实际编译器输出确认此方案可行，冻结 ISA/ABI、修正类型和链接脚本后才进入 S2；不能假定当前禁止 GOT 的 XIP 构建配置可直接复用。

### 4.2 ABI 合同

- 使用带 `version/size` 的 C 服务表和显式宽度整数；不跨边界传 C++ 对象、STL、异常、裸原厂地址或编译器私有布局。
- 最小入口为 create/start、受控事件处理、prepare_stop/stop、health；内存由分配方释放，所有资源登记到 App generation。
- 原厂地址适配只在固件中；App 通过服务 ID 调用网络、存储、显示、时钟及任务服务。按 ABI 主版本和 required-services 判断兼容，不要求精确固件 build 一致。
- 取消回调、关闭新请求、排空已入队请求与引用、释放任务/文件/显示对象后才可释放代码。停止超时不得强制 free 仍可能执行的代码。
- 无法排空时，由固件记录恢复意图并受控重启，启动时进入维护或选择旧包；不能在同一进程中冒险卸载。
- 无内存隔离不等于沙箱：业务代码内存破坏可能影响整机。看门狗与启动选择日志保证重启后可恢复，不能声称能在线隔离所有崩溃。

## 5. 包与持久格式

新格式暂名 APX2，与实验 APX1 明确区分，不兼容时显式拒绝。S1 冻结字节级规范和黄金样本：magic、格式/头长度、总长、App ID/版本、目标硬件/ISA、ABI 与必需服务、段偏移/长度/对齐、入口偏移、修正表、零填充大小、堆/栈上限、业务数据读写版本范围、内容 SHA256。所有长度相加检查溢出，段和修正目标不得越界或重叠写入禁区；先验证再分配。包摘要覆盖全部执行内容与兼容元数据（摘要字段采用规范化排除规则）。

完整性校验不代替来源认证；上传必须设备鉴权并核对 MAC。自用包不额外要求发布中心签名；未来签名策略不能封死原厂救援。固件返回自己的能力、包上限和资源限制，Bridge 不从模板猜能力。

持久目录逻辑角色如下，实际路径由固件存储适配统一定义：

| 角色 | 生命周期 |
| --- | --- |
| current | 唯一获准正常启动的 App 包 |
| incoming | 本次完整下载包，校验后作为候选 |
| previous | 本次更新的临时回退包；仅保留最近一次旧 App |
| transaction | 版本化、带长度/序号/校验的更新记录，记录新旧摘要及选择状态 |

这些是文件角色，不是预留的 A/B 分区。优先用同文件系统改名/角色转换避免额外复制；必须验证底层改名、同步与掉电语义，不能假定 POSIX 原子性。元数据采用小型双记录或等效提交日志，读回校验后生效；双记录不代表双 App 槽。无原子改名保证时通过日志和包摘要逐步恢复，不凭文件名判断成功。

任意时刻至多保留当前包和一个候选/旧包的完整内容；incoming 转为 current、原 current 转为 previous，不产生第三份完整复制。若存储实现不能保证此峰值，需要在 S1 明示实际额外空间并重新评审。成功清理失败只能保留上一旧包并上报，不允许无限累积历史包；下一次更新前先完成清理。

## 6. 更新、成功与回退

1. **准备**：鉴权、核对设备 MAC、能力、App ID、预期当前摘要、数据兼容与可用空间；创建原事务。下载阶段旧 App 继续运行。独立维护许可不要求业务 owner/context。
2. **下载**：分块写 incoming；只接受当前连续偏移或已接收且内容一致的重复块。写入/同步后才推进可恢复偏移；响应丢失查询原事务。总长、摘要、格式、ABI、预算全部通过才进入 ready。
3. **停止**：取得平台更新互斥，进入内置界面，拒绝新业务写入，排空所有资源。固件维护、原厂恢复和状态查询继续可用。
4. **切换准备**：持久记录旧摘要、新摘要及 `switch_pending`，读回后保留旧包为 previous，选择新包为 trial。任何一步断电都由日志与完整包摘要裁决；无完整可验证新包时恢复旧包。
5. **试运行**：先持久记录已消耗本次 trial 启动机会，再加载新包。初始产品预算为启动 10 秒、连续健康观察 30 秒；这些是待实机校准的目标，最终值随固件能力报告。健康要求入口完成、业务事件循环推进、原厂菜单/旋钮调度未被阻塞、维护可应答且无资源超限。不能要求 Bridge 在线、云端有数据或 Bundle 必须存在。
6. **成功提交**：固件依据同一 generation 与包摘要的健康结果，持久提交 `succeeded/current=new` 并读回。下载完成、HTTP ACK、start 返回都不是成功。客户端再认证同 MAC 查询实际运行 App 摘要/版本与事务结果。
7. **清理**：成功记录落盘后删除 previous 和临时下载信息；失败只报 `cleanup_pending`，不撤销已成功的新 App。清理中断可重复完成。
8. **失败回退**：提交成功前，启动失败、健康超时、重启或明确取消试运行时，持久记录回退意图，停止新 App、校验旧包并重新启动。回退完成终态为 `failed_rolled_back`，不能冒充更新成功。旧包也失败则进入 `recovery_required` 内置界面，继续提供独立 App 安装与完整 ROM 救援。

每个事务最多自动试启动新 App 一次、回退启动旧 App 一次；重启不能重置尝试计数。确认 succeeded 后不再依赖旧包，晚发故障只能重新安装已知可用包或恢复 ROM；若旧包尚未清理，也不能无日志任意改选。首次安装没有 previous，失败直接内置恢复。

### 6.1 数据与 Bundle 的回退约束

回退代码必须仍能读取数据。首期只允许新旧 App 都能读取的持久格式，试运行期禁止破坏性迁移和发布不兼容 Bundle；业务写入冻结到成功或回退完成，健康检查使用只读/内存态。固件的 Wi-Fi、鉴权与维护事务不归 App 回退，不复制整个设备配置。

后续若确需破坏性迁移，必须另行实现有预算的业务数据快照及恢复事务，在其验收前拒绝此类包。包声明与实际读写契约不符视为缺陷，不能依赖声明替代测试。成功清理旧包后仍需用户显式发布新的完整 Bundle；更新 App 不自动覆盖用户模板。

### 6.2 掉电恢复裁决

| 断点 | 重启行为 |
| --- | --- |
| 下载/校验前 | 正常启动旧 App；续传原事务或取消候选 |
| ready，尚未记录切换 | 旧 App 保持当前，等待明确提交 |
| switch_pending，文件转换中 | 核验日志指定的两个摘要；新包完整且未消耗 trial 才试运行，否则回退旧包 |
| trial 已开始，尚未 succeeded | 视为未通过验收，启动旧包一次；不循环重试新包 |
| 回退过程中 | 根据持久尝试标记完成回退或进入内置恢复，不反复启动崩溃 App |
| succeeded，清理未完成 | 只启动已提交新包，继续清理；不因旧文件存在回退 |
| 日志损坏、两个包均无效 | 内置维护；报真实校验阶段，禁止猜测当前包或伪造成功 |

## 7. 维护协议与并发

新增维护 API（拟定路径，S2 冻结线协议）：`GET /api/app/status`、`POST /api/app/update/begin`、`PUT /api/app/update/chunk`、`POST /api/app/update/commit`、`GET /api/app/update/result`、`POST /api/app/update/cancel`。复用固件维护监听和鉴权，不创建依赖 App 的第二套救援服务。

请求包含 device MAC、principal、operation_id；begin 固定 App ID、新包摘要/长度及 expected_current。事务命名空间按设备、principal、操作类型隔离。同 ID 同参数重放原结果，不同参数返回冲突；跨 principal 不泄露私有回执。chunk 带 offset 和块校验。commit 只启动一次切换；重复调用返回当前阶段。cancel 在提交成功前按状态回退，成功后返回明确终态，不删除 current。

响应统一返回 operation_id、phase、state、error_code、retryable、下一步和当前/目标摘要；202 表示进行中，成功终态仅为 succeeded，失败回退单列。客户端请求初始上限 15 秒，状态查询有退避与总预算；网络超时只查询原事务，不换 ID 重发。回执过期返回 `receipt_expired` 并指导读取运行状态；旧 ID 的提交必须受预期摘要和已提交序号围栏保护，不能因缓存淘汰重新执行。

固件互斥覆盖 App 切换、Bundle 安装与原生 Flash 写入。下载是否与业务共存取决于实测 I/O 预算；真正切换才暂停业务。每阶段有期限并返回真实失败阶段。结果未知不无限占用互斥：先在固件内核验日志/实际 I/O，确认写入结束或安全重启后释放，不能在 Flash 仍写入时强行解锁。

显式完整 ROM 救援可中止下载或安排安全重启；不得被 App 健康/稳定记录/业务 owner 卡住。普通 OTA 仍禁止写当前运行槽或用户保留槽，并核对长度、边界、完整性与身份。恢复 CLI 和设备菜单应与 Bridge 共用维护服务，Bridge 不在线不影响恢复。

## 8. 资源预算与测试

设旧包 O、新包 N、日志及存储保留量 R；更新前新增可用空间至少 N+R，峰值完整包存储 O+N+R。成功后只保留 N+R。首装为 N+R。存储不足在停止旧 App 前明确拒绝，不能自动删除唯一可用旧包凑空间。

下载阶段 RAM 为旧 App 运行量加有界收包/摘要缓冲；停止排空后释放旧 App，再分配新代码/只读段、data/bss、堆和任务栈，不同时驻留两份运行实例。回退同理先释放新实例。日志不持久化原生 struct，按实际数量记录修正/授权/事务；栈不用完整包局部数组。

S1/S3 必须交付首装、最小 App、真实典型 App、允许上限包的存储字节、峰值 RAM、任务栈高水位、耗时与碎片情况；当前数值未知，不以桌面模拟替代实机。预算必须为内置维护与原厂界面预留，OOM 进入可查询失败或回退。

测试矩阵至少覆盖：格式损坏/截断/溢出/未知版本、非法入口/修正、错误 MAC/token/principal、撤销授权、重复块/冲突块、重复提交/过期回执、磁盘满/分配失败、停止卡住/悬空回调、每个持久写入与文件转换前后掉电、新 App 崩溃/健康超时、回退失败、清理中断、数据回退兼容、并发 Bundle/ROM 更新，以及无 App/无稳定记录的维护和原厂恢复。宿主测试、RV32 执行测试和同机断电/救援分别记账。

阶段按顺序推进；可以先做 S4 的离线打包适配，但不能绕过 S1/S3 准入。本次只交付 S0，其他阶段未实施。跨仓代码改动时运行 codex_status 的 `python tools/test-ap01-firmware-boundary.py`，相关 UI 改动另按所属仓库要求验收。

### 9.1 首次平台迁移与救援顺序

当前部署事实须在操作前重读交接并认证核对，不能使用旧 IP 推断。先验证不依赖新 App 的现有恢复入口，再迁移加载器平台。保留 0031 救援底座，不要求它支持业务协议。

交接记录为运行槽 1、用户保留救援槽 0 时，两槽不能直接任选覆盖。候选路线是先通过现有入口明确切至救援槽 0，确认原厂功能与可用升级通道，再把新平台写入此时非活动的槽 1；全过程不写保留槽 0。这只是待操作前核验的路线，未证明 0031 当前可接受该镜像前不得执行。若现有入口不支持，停在原设备状态，另行确定救援路径，不能违反运行槽/保留槽保护。

平台 ROM 上线后，演练普通 OTA 写非活动且未保护槽、无稳定记录手动切槽、App 不启动仍可安装、失败后继续救援及保留槽不变。实际可写目标不足时先明确测试槽位安排，不以模拟通过冒称全部同机通过。新入口同机验证前不关闭旧入口。稳定确认仅启用自动 ROM 回退，不作为普通 OTA/手动切槽前置条件。

## 10. 本次审阅结论

设计明确允许临时旧 App、失败回退和成功后清理；无固定 App A/B 槽。剩余首要技术不确定性是实际可执行内存与完整 App 预算，其次是文件系统断电语义和彻底排空现有回调。它们是 S1/S2 的可验证交付，不能标成“功能已有但未启用”。当前代码未修改、未构建、未部署；阶段状态见 [status](status.md)。
