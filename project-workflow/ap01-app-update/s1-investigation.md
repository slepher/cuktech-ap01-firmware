## 最小验证顺序及通过条件

### 1. 恢复可复现构建基线

同步并核对已有统一构建变更和依赖，安装/指定可在本机运行、支持实际 RV32 ISA 与 ilp32f 的交叉 C/C++ 工具链及 binutils。先复现平台版和当前 App 版的 audit → link → package → candidate validation，保存工具版本、两仓提交/工作区差异、源文件摘要、ELF/map、段大小、未解析符号和栈使用文件。产物保持离线候选。

基线构建通过后才对受限 PIE 参数做对照实验。原 XIP 构建保留为基线，不直接改其链接规则。

### 2. 先确定内存区域，再做最小取指实验

先恢复/核对 0041 内存映射、原厂分配器、内存权限配置和缓存维护证据，确定候选 SRAM/PSRAM 区域及保留范围。当前没有可以宣称安全的可执行 RAM 地址。不能盲扫地址或在维护会话里直接跳到任意 malloc 指针。

准备最小、显式触发的 0041 平台实验：在经核实的区域内分配并对齐小段代码，复制只返回已知值的叶函数，按核实的缓存流程同步后调用；记录真实地址、分配长度、对齐、返回值与故障阶段。使用同一缓冲区换成另一返回值再调用，检查旧指令缓存问题。仅靠一次 `fence.i` 不能预先证明芯片所有缓存/映射场景正确。

后续逐步加入 C 服务表间接调用、只读数据、显式可写状态及受控调度；记录中断/任务切换后的正确性、维护响应和原厂菜单/旋钮可用性。分配与释放保存原始指针，入口对齐和缓冲区有效范围单独验证。实验必须先确认已有救援可用，并确保异常或看门狗复位不会再次自动跳入崩溃代码。

通过条件：0041 实机可重复从已知区域执行，并得到缓存、权限、对齐和调度证据。最小函数通过仍不代表真实 App 能装入。

### 3. 真实 App 受限链接与两基址执行

以当前工具链实际输出为依据，尝试 PIE/hidden/medany、禁 relax、小数据阈值 0；检查 C++ vtable、函数/数据指针、GOT、libgcc 辅助函数、全局初始化及原厂导入。固件适配保留在平台内，App 仅经稳定服务表导入；不能把原厂绝对地址包装进 App 修正表。

保存完整 ELF 重定位列表及每种类型的来源，将内部基址和服务引用规范化为有界修正记录。对于未定义类型、越界、重叠或禁区目标明确拒绝；此时再决定允许 GOT 的受限布局，而非沿用原 XIP 的禁 GOT 假设。设备不解析通用 ELF。

先用最小包在 RV32 执行环境中验证两处基址、data/bss 初始化和错误修正拒绝，再在实机验证相同性质。随后用真实业务 App 测量完整代码/rodata/data/bss、堆、栈高水位、最大连续分配、重复装卸碎片、加载时间和事件处理延迟，为维护与原厂 UI 留余量。旧实例排空后再装新实例。

通过条件：真实规模 App 能运行且预算可接受；若执行内存容量/权限不成立，停止此后端，评审替代方案，不转为固定 App 双槽。

### 4. 存储持久性实验

使用同一 `/resource` 挂载下隔离的实验目录和模拟包，避免触碰运行 App、Bundle、授权和唯一有效旧包。先测试短写、sync 失败、空间不足、同目录改名/覆盖/删除及读回摘要；再在每个写入、同步和角色转换前后实机掉电。

重启后按版本化双记录/日志及内容摘要判定完整包，不能只看文件名。记录实际占用、峰值空间和损坏形态，证明最多 O+N+R、清理可重入以及未完整新包不影响旧包选择。若底层需要额外完整副本，停止并重新评审空间设计。

### 5. 冻结 S1 输出

完成上述编译器与实机证据后，冻结 ISA/ABI、受限链接脚本、APX2 字节布局/摘要覆盖规则、修正类型与黄金样本，并提交首装、最小、真实典型、允许上限包的资源表。包上限以 0041 实际测量结果确定，当前不提前冻结。

## 本轮结论

验证路径可落在现有固件适配与构建链上，但本机首先需要补齐统一构建提交和交叉工具链。0041 可执行区域、完整 App 容量、缓存/中断安全与存储耐断电性均未证明；S1 保持进行中，S2–S5 不进入实现或部署。硬件实验前重新读取交接并认证同 MAC/槽位，遵守设计第 9.1 节救援与保护槽约束。
