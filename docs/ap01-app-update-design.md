# AP01 独立 App 更新与恢复设计

修订：2026-11-03，重启切换与多 App 版本集合。本文定义目标方案，不表示实现完成。D0 文档与 D1 非实机纵向验收已完成，D2–D4 待推进，部署状态不变。

本版替代此前“单运行 App、在线停止/排空/卸载”的目标。历史见 [旧设计](../project-workflow/ap01-app-update/design-hot-unload-history.md)，实际证据见 [状态](../project-workflow/ap01-app-update/status.md)，实施顺序见 [计划](../project-workflow/ap01-app-update/plan.md) 与 [任务](../project-workflow/ap01-app-update/task.md)。

## 1. 目标与范围

核心诉求：业务变化只交付独立 App 文件，不再每次构建和刷写约 7 MB 的完整 ROM。允许提交后重启；不追求在线热卸载或无感切换，不承诺尚未测量的重启耗时。

现有设备需先安装一次具备加载器和独立维护能力的 0041 平台固件，之后兼容 ABI 的业务更新才只换 App 包。0031 不部署 App，不参与 App 加载验证；保留既有 ROM 救援与槽位保护，App 更新不改变原厂 A/B ROM 布局。

本期支持激活列表中的多个 App 开机加载、共用现有界面宿主；可更新其中一个，也可一次提交多个 App 的更新。单个更新是批量事务的单元素形式。首次安装允许从空集合加入 App；本期不增加独立的卸载、任意启停、市场或跨设备批量发布功能。后台任务可共存，前台页面由宿主统一调度，不能将“多 App”理解为各自直接接管原厂 UI。

当前授权已恢复 D1：真实 App 的 C 函数表、独立打包与开机加载。后续非实机目标包括代码、打包、firmware OTA CLI 和离线/模型端到端验收；实机刷写、迁移、掉电演练不在当前范围，不能用模型结果替代硬件准入。

## 2. 复用现有多 App 框架

复用 [screen_host_0041.h](../tooling/firmware-modules/screen_host_0041.h)、[screen_host_0041.c](../tooling/firmware-modules/screen_host_0041.c) 的 App 数组、页面集合、轮询与切换，以及 [双 App 测试](../tooling/firmware-modules/test_screen_host_0041.c)。现有 codex_status 普通构建注册一个 App，AP01_SCREEN_HOST_PROBE 注册第二个测试 App；这证明宿主已有多 App 接口，不证明多个独立文件包已安装运行。

目标是由常驻平台创建唯一宿主，开机按 Manifest 的确定顺序加载 App，再为各 App 注册自己的页面集合；App 只获得本 App 的注册上下文。现有页面切换/销毁保护仍用于正常 UI 行为，不为更新增加动态撤销全部代码回调的链路。App 注册失败视为启动失败；本次启动内不释放其代码或尝试原地重新加载。

平台统一分配 App 身份、私有存储根、任务预算和网络资源。重复 ID、端口或其他独占资源冲突在提交前拒绝，遗漏到启动阶段的冲突使整个候选集合失败。不得复制多份绑定相同 HTTP/发现端口的 Runtime 来冒充多 App 接入。

## 3. 固件、App、Bundle 和客户端边界

| 组件 | 职责 |
| --- | --- |
| 固件平台 | 原厂菜单/旋钮与唯一界面宿主、Wi-Fi、维护监听/鉴权、加载和启动监督、Manifest/事务、重启/回退、ROM OTA 与救援 |
| App | 业务通信、配对交互、Bundle/模板显示及本 App 数据；通过平台 C 接口注册页面、创建任务和访问资源 |
| Bundle | 模板、字体与数据合同；保持独立发布，不因 App 更新自动覆盖 |
| firmware OTA 客户端（本仓） | 选择单包或多个包、读取能力、核对 MAC、持久保存原事务回执、续传/重连及显示真实结果 |

维护监听、设备码鉴权和恢复入口必须在 App 加载前建立，不调用 App 的 owner/context 才能完成安装。配对产生的维护授权仍由平台独立持久保存/撤销，不能复制凭据仓库或回退固件授权状态。具体授权集成须审计现状，不以已有设备码路径代表全部完成。

App 与固件处于共享地址空间，不是安全沙箱。边界用于兼容性、资源预算和职责划分；不声称能在线隔离野指针。启动监督、独立看门狗和持久恢复决定用于故障后恢复。

2026-11-05 仓库边界收敛：App OTA 含客户端归 firmware；codex_status 保留业务 Bundle 协议和必要 App 适配。Bridge App OTA UI/worker 已撤出；完整目录扫描和桌面产品化不作为独立业务主线前置。见 [归属与当前主线](app-ota-ownership.md)。

## 4. 执行模型与直接 C 函数表

### 4.1 每次启动加载一个确定的 App 集合

文件包 → 校验 → 固件管理的可执行内存 → App 入口。运行期间不替换、卸载或释放已进入 start 的 App 映像；更新、失败回退或运行故障通过重启处理。一个启动周期不能先运行候选再原地装入旧集合。

可执行池按各包 image+bss 和对齐顺序分配；只用于启动时加载，不需运行期压缩。池的具体地址、容量、分配方法与缓存同步由后端验证决定，不能直接声明一个普通静态数组就是可执行内存。堆、任务栈和平台预留另外计入总预算；线性代码池不能证明堆无碎片。

S1 硬件准入仍未通过：0041 可执行内存权限、容量、缓存/中断安全及真实 App 预算必须另行实测。离线实现允许继续，但产物保持不可部署状态；硬件条件不成立时评审替代后端，不暗改 ROM 布局。

### 4.2 版本化 C 平台 API

目标采用带 abi_major、abi_minor、struct_bytes 和能力位的 C 函数指针表（暂名 Ap01PlatformApi；入口主版本已定为 3，平台函数表 3.0 已冻结），配合每 App 上下文。直接调用时钟、随机、文件、网络、任务、UI、日志与分配接口，不再要求 service/op/input/output 的统一报文封装。

接口约束：显式宽度类型、明确缓冲区长度/返回值/所有权、调用线程约束和阻塞期限；不得跨边界传 STL、异常或编译器私有对象。文件/UI 对象可用 opaque handle 或明确冻结的 C 结构，优先适配现有宿主接口，不把原厂内部结构全部暴露出去。表只允许兼容追加，缺少必需能力明确拒绝；不匹配精确固件 build。

App 入口已固定为 start(api, app_context, out_instance)、event 与 health，详见 [ABI 3.0 合同](app-platform-api-v3.md)。不再要求为更新实现 prepare_stop/stop；正常资源关闭仍由对应 API 提供。任务/UI 回调允许存活至本次启动结束。旧 ABI v2 五入口与通用 invoke 的包不得被静默解释为新合同；已实现 APX2 容器 2 / ABI 3 的 start/event/health 三入口编码，旧入口执行器拒绝 ABI 3。详见 [D1 记录](../project-workflow/ap01-app-update/d1-direct-app.md)。

malloc/free 等可通过平台配额包装；保留平台维护内存和每 App/整机预算，不能裸透传导致业务耗尽维护资源。C++ new/delete 的本地薄适配和 libgcc 编译器辅助函数仍可能必要。格式化等优先复用平台实现，确需可变参数接口时固定 RV32 ABI 并验证；不为消除导入继续自研完整 libc。数学、GOT、虚表/数据指针和全局初始化逐项审计，不能由函数表替代最终链接证明。

## 5. 单包、Manifest 与存储

APX2 继续作为单 App 扁平包容器，保留流式完整性校验、有界 BASE32 修正和包预算。现有 [APX2 v2 规范](apx2-package-format.md) 是旧 ABI 实现记录；新入口合同冻结后决定保持容器布局并变更 ABI 主版本，或升级容器格式。设备不解析通用 ELF。

新增版本化 Manifest，表示一次开机要运行的完整集合。D2 已实现 [AMF3 编码/全包预检](app-manifest-v3.md)，生产多槽接线尚待完成。逻辑字段至少包含格式/序号、条目数、按 app_id 排序的唯一条目、每项包摘要/长度/版本、启动顺序、ABI/数据兼容与资源声明；定义确定性编码及摘要覆盖，不哈希不规范 JSON。条目数量上限与总包/RAM/任务/端口预算由能力报告给出，不凭空承诺 4 或 8 个 App 能运行。

更新请求给出 expected_current_manifest 和本批变化项。固件将变化项合入当前集合，生成完整候选 Manifest；未更新 App 保持原摘要。整套集合检查重复 ID、完整包、兼容合同和总资源上限。首期跨 App 持久共享数据不受支持，通信协议存在依赖时须声明可验证的版本约束；不能仅凭整批回退推断兼容。

存储采用按摘要标识的完整包与独立 Manifest，current/candidate/previous 是集合角色，不是固定 App A/B 分区。未变更包被两个 Manifest 共同引用，无需重复复制。各包下载使用有界临时文件，完整校验后发布；角色是否有效由已提交日志和摘要决定，不依赖改名原子性的猜测。

设当前唯一包集合 C、本批新增不同摘要包 U、元数据与保留空间 R，峰值空间为 bytes(C∪U)+R；新增可用空间至少 bytes(U)+R。临时下载到发布不得再复制一份完整内容，实际文件系统无法做到时必须重新计算并提前拒绝不足空间。至多保留已提交集合和一个候选/回退集合，旧包清理失败阻止下一事务，不自动删除唯一可用包腾空间。

## 6. 重启切换与集合原子回退

1. **准备和下载**：鉴权/MAC/能力/预期集合检查后创建原事务；按包 ID+摘要分块续传，所有变化包和候选 Manifest 校验完成才 Ready。当前集合可继续运行。
2. **提交**：进入平台共享维护执行序列，禁止新的冲突写操作，等待已开始的持久写入完成并同步。不能等待的写操作使提交返回 Busy/失败，不可强制重启打断。候选 Manifest、包和所需元数据持久完成后，写 SwitchPending 并读回验证。
3. **重启安排**：返回 202/reboot_pending 并安排有界延迟重启。ACK 丢失、客户端离线不撤销已提交决定；重复 commit 只返回原事务，不重复创建切换。重启安排失败明确可查询并重试，不能无限等待客户端 ACK。重启前当前集合仍是旧实例，状态须区分持久意图与实际运行集合。
4. **开机裁决**：先建立维护，读取日志/Manifest 并重新校验全部包。在任何候选 App 执行前，持久记录 TrialStarted、启动机会已消耗并读回；按确定顺序加载/启动整个候选集合。失败不在当前启动内卸载或启动旧集合，而是记录回退意图并重启。
5. **健康观察**：所有激活 App（含未更新项）的入口和事件推进、平台原厂调度与维护心跳均满足预算才允许成功。暂沿用全集合启动预算 10 秒、全体就绪后连续健康 30 秒、总预算 40 秒；必须用实际多 App 测量，不能把每 App 预算相加后暗中放宽。Bridge/云端/Bundle 缺失不应导致健康失败。
6. **成功**：持久提交 Succeeded 与候选 Manifest 为 current，读回后开放试运行写权限，清理不再引用的旧包及临时文件。正常成功无需再次重启。清理失败只报 cleanup_pending，不撤销成功；历史成功和当前运行健康分开报告。
7. **失败回退**：试运行失败、取消或重启发现 TrialStarted 未成功，选择事务的完整旧 Manifest，绝不逐 App 拼装新旧版本。先持久记录回退启动机会已消耗，再执行旧集合；最多一次 trial 和一次 rollback。旧集合启动失败或记录不可判定则进入内置维护，不循环重启。

初装旧集合为空，失败进入维护；批次新增 App 回退后自然不在旧集合中。单个更新也回到事务开始前的完整集合。Succeeded 后的晚发故障不自动复活已清理旧包：进入恢复并显式重新安装。

### 6.1 事务存储与掉电

复用 AUT2 的双记录、序号/CRC、同步读回、Unknown 状态处理和防循环思想，不能原样复用其单个 old/new digest 布局。新集合日志须引用旧/候选 Manifest 摘要、事务身份和阶段/启动次数；Manifest 持久完成先于引用它的日志，格式版本和旧记录处理显式定义。每包续传进度的持久格式单独冻结，不塞进无限增长的内存结构。

| 掉电位置 | 下一次启动 |
| --- | --- |
| 下载/Ready，尚未提交切换 | 启动已提交旧集合，原事务可续传/取消 |
| SwitchPending，尚未消耗 trial | 校验完整候选，持久消耗一次机会后试运行；缺包则进入回退裁决 |
| TrialStarted，未成功 | 不再试候选，持久消耗一次 rollback 后启动旧集合 |
| rollback 已消耗但未完成 | 恢复界面，不反复尝试旧集合 |
| Succeeded，清理中断 | 只启动已提交新集合，幂等继续清理 |
| 日志/Manifest 不可判定 | 保持维护可用，禁止猜测或扫描文件自动选“最新版” |

受控重启无法解决所有卡死；监督与看门狗必须不依赖 App 线程。需要证明失控 App 无法通过停止自身 health 调用无限阻止恢复，模型不能覆盖的硬件看门狗证据单独列为实机项。

### 6.2 数据和 Bundle

本次不采用未经审计的“小状态文件 .bak 还原”。首期保留试运行禁止破坏性持久写入的政策：整个候选集合的业务写入冻结至成功或回退健康完成，禁止配对提交、Bundle 发布和不兼容迁移；业务可以加载已有数据、显示和进行只读健康运行。未更新 App 同样受此门约束，避免集合级回退时共享副作用失控。

实现收敛为直接 C 文件/写服务的一处权威写许可，业务只保留必要的只读启动和拒绝写请求提示，不继续扩展报文/代际冻结层。权限开放失败不可对外宣称业务已可用，持久成功不能因此倒退；进入可查询恢复状态。

包声明须兼容现存数据，尤其不能撤销固件 Wi-Fi/鉴权状态。未来若采用快照，必须先枚举写集、存储预算、备份/恢复掉电步骤和对外已确认操作的语义，另行修订并验证，不能仅增加 .bak 后缀。

## 7. 协议与客户端

沿用独立维护监听、设备码鉴权和 begin/chunk/commit/result/cancel 职责，目标线协议必须显式版本化；当前 [HTTP 文档](app-update-http.md) 记录的单包字段不能直接当成多包协议。

- status：协议/ABI/包格式、App 数/空间/资源上限、当前持久 Manifest、boot_id、实际运行 App 列表（ID/摘要/版本/健康）、维护与事务阶段。
- begin：MAC、operation_id、expected_current_manifest、变化项列表及候选集合身份；同 ID 同参数幂等，不同参数冲突；一台设备至多一个更新事务。
- chunk：明确事务和目标 App/包摘要、偏移、块 SHA；包之间不得混写。续传按每包持久偏移查询。
- commit：整个候选集合 Ready 后一次提交，返回重启意图；不提供逐项提交造成半批成功。
- result：报告旧/候选/已提交集合、每包接收状态、trial/rollback/cleanup、实际 boot_id/运行列表与错误；回退不能显示成功。
- cancel：提交前仅删除未引用候选；SwitchPending 未进入 trial 时持久撤销后恢复旧集合选择；候选已执行则持久安排重启回退；Succeeded 后不撤销。

同事务 MAC/principal/操作类型/参数指纹隔离，提交围栏比较 Manifest 摘要和序号。firmware OTA CLI 在 mutation 前持久保存回执；重启断连按原事务重新认证查询，不换 ID、不把连接断开当失败重装。202/下载完成/重启完成都不是成功；成功须同时核对持久新集合和实际运行列表，历史成功但当前不可用必须如实报告。

App 提交、Bundle 写入、ROM Flash 操作与 Wi-Fi 变更共用平台协调，下载是否允许并行由资源/I/O 预算决定。忙状态不得封死查询和救援；ROM 救援可安全取消下载或安排重启，但不得中断尚未完成的 Flash 写入。运行槽和用户保留槽保护不变。

## 8. 复用、冻结和迁移原则

| 资产 | 处理 |
| --- | --- |
| 多 App screen_host、页面切换与输入调度 | 直接复用，移至唯一常驻宿主并接独立包注册 |
| APX2 校验/加载、离线修正、SHA 与故障测试 | 保留并按新 ABI/真实多包补充验证 |
| AUT2、下载、选择、HTTP/CLI | 复用算法与测试场景；显式升级集合格式、重启语义及协议 |
| 独立维护鉴权、ROM 保护、Bundle 边界 | 保留，不因架构简化削弱 |
| 热卸载 generation/lease/prepare_stop/drain 链路 | 不再作为新方案验收目标；待生产路径迁移后移除专为卸载存在的代码 |
| 文件/网络/堆通用 invoke 与客户端报文 | 迁移为直接 C 接口，保留必要权限、期限、配额与正常 close |
| 私有 snprintf/完整 libc 扩展 | 停止扩展，优先平台导出；编译器辅助及必要本地薄适配按最终链接决定 |
| UI 销毁保护、普通锁、业务只读恢复 | 按实际用途保留；不能把所有安全检查归为热卸载而批量删除 |

旧测试通过只说明旧路径的性质，新路径必须重验。旧源仍在工作树，本次文档更新不表示已删除、旁路或完成迁移。

## 9. 实施顺序和验收
