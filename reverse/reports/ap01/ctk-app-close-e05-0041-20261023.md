## 真实 app 和 DELETE 的连接

`a005cd68` 取得 `a008184e()` 返回对象，经栈保存后于 `cd78/cd7c` 作为 parent 传给 `a00b2f6c`；返回于 `cd80:2a8a` 保存在 s4。这正是 `a005d140:d285` 传给 item 注册器的 userdata。`cd82:2145` 与 `cd84:ef10e35d` 另分配8 B state，`d122` 重读该指针，`d12c:2328fa00` 写入 app+0x10。这里 app 是 GUI window 对象，state8 不是 app 本体，也不是子页20 B wrapper。

`a00b2f6c(parent)` 以 class=`a05647fc` 调 `a00d76ae(class,parent)` 并初始化对象。原 class 表：base=`a0263ef4`，constructor=`a00b1d78`，destructor=`a00b1df8`，event=`a00b1e54`。class+0x20 的原 word=`0x681`，分配器 `d76c8..d76da` 实际提取 bits19..4 得实例大小0x68 B，再交给 `a008e38c`。`d76e2/e6` 写 app.class 与 app.parent。

正常非空 parent 分支 `d77be..d7804` 确保 parent+8 扩展存在，读/加/写扩展+0x30 的 u16 child_count，按 `count*4` 调 realloc 并把 app 追加进 child array。app 因而有对象树持有边，而不只靠订阅节点存活。`b2f90` 调 `a00d733a` 得到独立输入/组关联句柄 G，`b2f9e` 将 G 保存 s1；`b2fa2` 保存原 `62fc95bc` 到 app+0x2c，`b2fa6` 将仍在a0的 G 写入 `62fc95bc`，`b2fde` 将 G 写入 app+0x30。该全局保存的是 G，不能画成持有app的根。此处“持有”指原程序保存指针，不代表引用计数 retain。

初始化 `a005d0f2..d11e` 建立两个不同 timer：

- `T1 = a008bc64(a00af262,1000,app)`；返回保存 s1，随后成为 DELETE 的 userdata。
- `T3 = a008bc64(a00abd9c,3000,app)`；返回写 app+0x58，紧接调用 `a008bd16()`。本轮不把该无参数调用命名为对全部 timer 的销毁。

`d13c/d142` 合成 item callback=`a00adabc`，`d140` a1=app，`d146/d14a` 同一 AUIPC/JALR→`a01b28ce`。后续 `d172..184` 注册输入 callback=`a00afc88`、filter0x11、userdata0；`d188..19c` 注册 **`a00ab8ec`、filter0x29、userdata=T1**，a0仍是同一 s4 app。

`a01ad654(obj,cb,filter,userdata)` 正常段确保 obj+8 存在，以其+8事件列表调用 `a01b93b4`。descriptor的三word写入 `a01b9432/9438/943a` 为 callback@0、filter@8、userdata@4。上层未检查安装返回值；静态可证明挂接意图和 ABI，不声称已观察运行时安装成功。

`a00ab8ec` 先对 `event+8 & 0xffff7fff` 比较0x29，不匹配直接返回；匹配后从 **event+4 original target** 取 app，从 app+0x10 取 state。state为0只日志返回；state非0后从 **event+0xc userdata** 取timer，timer为0也日志返回，且这条分支不free state、不清app+10。两者非0才执行下面的原顺序：

```c
// 分析重建，并非原源码；仅已核DELETE局部。
app_delete(e) {
    if ((load32(e+8) & 0xffff7fff) != 0x29) return;
    app = load32(e+4);
    state = load32(app+0x10);
    if (state == 0) { log_missing_state(); return; }
    timer = load32(e+0x0c);
    if (timer == 0) { log_missing_timer(); return; }
    a008ae58(timer);       // dtor参数不是app，也不是state
    a008ab8a(state);       // 原a00ab95e将s2放a0
    store32(app+0x10,0);   // free之后清，不能调换
}

timer_delete(timer) {
    a0089d02(0x62fc95f0,timer); // only unlink
    store8(0x62fc95fe,1);
    a008ab8a(timer);             // separate free
}
```

交付ABI有直接原证：`a008ad8e..ad98` 从descriptor+4取userdata→写event+0xc→a0=event→从descriptor+0取callback间接调用；紧接读取event.flags，不使用callback数值返回。因此不能把 `free()` 的残余 a0 或 callback无定义返回解释成DELETE成功码。核心删除器 `dcf88` 检查的是事件发送器 `a00d831a` 返回状态：0时清删除位并返回；非0才继续。

条件正常的对象删除次序为：设置 obj+0x2a 的0x1000位→同步0x29事件→清事件列表→反复 child(obj,0) 递归删除→必要输入/动画解绑→`a00d7806(obj)` class析构→从父child array或display screen array移除/realloc→`a008ab8a(obj)`。因此真实 app DELETE state free 若被交付，发生在其子页DELETE/析构和app对象free之前；这只是**对象被正常公共删除器删除时的条件次序**，不是已找到哪个正常退出调用者会对这个注册app调用删除。

class析构器按 class+8 以 `(class,obj)` 调用，之后把 obj.class 换成 base class递归。window dtor先读取 **app+0x60** 的独立class timer，有则 `a008ae58`；再把 app+0x2c 的旧输入/组句柄写回62fc95bc，对type4输入设备解除app/重挂旧句柄，最后对app+0x30调用 `a00d8370`。这里的class timer与T1和app+0x58的T3是三个不同字段/挂接来源，不能合并成一个timer。base dtor标记活跃事件对象删除，并清样式/事件列表/child-array扩展等内部资源；未读app+0x10来代替业务state回收，也没有读取62fcb530。未据此认证所有下游通用辅助的跨函数副作用。

## item 节点究竟有没有注销/归还

节点布局沿用E03/E04：16 B `{callback@0,app@4,prev@8,next@12}`，head=`62fcb530`，head.link_offset=8，head.first@4、last@8。`a01b28ce` 按callback而非 `(callback,app)` 去重；命中直接返回，不更新旧app。未命中通过 `a008af14(head)` 分配 `link_offset+8=16` B并追加；随后无新增非空门地写callback和app。node保存app只是一条借用边，没有retain或析构回调。

原指令搜索发现该头确有另一内联移除点：`a00f2f98`，但 `f2fa4/f2fa8` 合成比较键 **`a00f5288`**。相等才以 `(62fcb530,node)` 调 `a0089d02`；随后 `f2fbe/f2fc0` free的是此前保存s2的页面业务数据，不是node。这个片段既不能证明 `a00adabc` 被注销，也不能将后面的free挪到node。`a0089d02` 及其两个link setter完整窗口没有allocator/free调用：first、last或中间节点分支只更新head与邻接link，故“摘链”必须和“归还node”分开。

本轮有界原字节搜索范围 `[a0000000,a01b9800)`：半字对齐寻找 LUI62fcb000，随后34 B内寻找同rs1的I类 load/addi，立即数530..53c，共16个候选。人工区分：530真正用途为item dispatcher、head初始化、注册器、上述另一callback的inline remover；53c属于相邻通知头。`a00ab18e→ab1a0` 为false positive，a5已被 `c.lui a5,7` 覆盖，实际常量是0x7530。`a00a5640→5656` 跨另一次同寄存器LUI，最终指向同一初始化，不是独立引用。

该方法不覆盖通过全局指针别名、间接参数、其他寄存器算术、较长常量构造或运行时计算取得head的路径；不声称穷尽引用。retained `a00adabc` incoming仍只有 `a005d142` PARAM/data一条，direct callers为空。DELETE callback的完整原字节已经排除其直接调用注销器；不能据此宣布全程序从不注销、永久常驻或泄漏。

未知、且本题保持断开的边：

1. **正常退出触发者→这个注册app的公共DELETE。** 找到实际DELETE安装，不等于找到对该app的实际离页删除。`a00afc88` 是输入挂接身份；其retained大函数只用于有界定位，不能把其中其他临时窗口的删除参数认作这个app。初始化8B分配失败附近的 `a00d7806(app)` 是直接class析构，也不是正常退出或公共DELETE，不拿它充当目标路径。
2. **`a00ab8ec`之后→以key=`a00adabc`或userdata=`app`注销62fcb530节点。** 该callback完整实现无此边，window/base析构已核指令也未直接访问该head。需要追其他head别名/teardown真实caller，不能接 `a01b2966`（它是62fcb554控制链）。
3. **item node最终free、T3归还与子页业务context最终free。** node摘链与内存回收是两个问题；本轮未证实目标node被摘链。子对象本体递归free不证明其wrapper/context全被free；不把free(state8)、free(obj)或class timer free代替这些资源。
4. **callback期间可达性/调度同步。** 已见dispatcher保存node并在callback后重读link，无refcount或detach保护；没有静态调度完整合同来证明目标app退出与item通知不会交错。未作异常、竞态或缺陷判断。
