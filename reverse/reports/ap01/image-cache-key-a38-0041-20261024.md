## 真正新增：默认安装、字段与返回

A23 已知创建器收到 callback 表。创建正常路径 `a01985d6..85e2` 以 a2=12、a1=原表、a0=cache+10 调 copy adapter，将三个 RV32 word 复制到 cache+10/+14/+18；随后 backend initializer `(cache)`。此处 source 表身份继承 A23/A27，不把诊断失败路径扩成签名保证。

`a00f0d26` 从 cache+10 读 comparator 到 a1；正常有效输入到 `a00f0de0..de6`，a0 改为 cache+24，a2 为既有 cache+4 加0x14，调用 `a00f0b80`。其正常设置窗口 `a00f0c02..c1c` 保存原 a1，并清 tree+0、写 tree+4=原 comparator、tree+8=原 a2。因此默认初始值满足：

```c
load32(cache+0x10) == load32((cache+0x24)+4) == 0xa0087bc6;
```

这是初始化时的同函数绑定，不保证动态重配后永远相同。

`a0087bc6` 适配器的必要字段窗口 `7bce..7bda` 顺序为 LBU right+8→a3、LW right+4→a2、LBU left+8→a1、LW left+4→a0，调用 `a0087b5c(sourceL,classL,sourceR,classR)`，原样返回其结果。class 是零扩展8位，不是整个32位 word；source是32位word；+0、+9..+b、pixel/decoder/user_data 均不在本比较器中读取。

以下仅为原核心控制流的结构化描述，不是原源码：

```c
int32_t compare_record(const void *left, const void *right) {
    uint32_t sL=load32(left+4), sR=load32(right+4);
    uint8_t cL=load_u8(left+8), cR=load_u8(right+8);
    if(cL != cR) return cL > cR ? 1 : -1; // unsigned class ordering
    if(cL == 1) {
        int32_t r=a002db16(sL,sR);
        return r==0 ? 0 : (r>0 ? 1 : -1);
    }
    if(cL != 0) return 0; // 原 7b8c 非零门，不替原行为补比较
    if(sL == sR) return 0;
    return sL > sR ? 1 : -1; // BGEU，unsigned RV32 source values
}
```

同class非0/1直接0是原指令的有限合同，未研究其正常调用协议，也不外推它们的图像格式行为或构造路径。class0比较没有解引用描述符或逐字比较 PNG 数据：两个内容相同但地址不同的 descriptor 在这个比较器中不相等。此为静态比较条件，不是人为重复 insert 实验。

### class1 为什么可称内容比较

未凭函数名假设 strcmp。实际调用 `a0087b70→a002db16`；必要窗口显示：入口 OR 两地址后 AND3，未同时4字节对齐则进入 byte loop；对齐时两个 LW 相同后走零字节检测，不同则落 byte loop。`a002db3e/db42` 原字节 `8b47e580/8bc6e580` 独立位域核为 shift0 的 `th.lrbu a5,a0,a4`、`th.lrbu a3,a1,a4`。索引 a4 初值0，左 byte为0即结束；否则右 byte相等才递增索引继续；不等结束。`db4e` 返回两零扩展 byte 的差，范围−255..255；适配器按 signed 正负归一成−1/0/1。

对齐的相等word路径 `db58..db6e` 使用 `(word + 0xfefefeff) & ~word & 0x80808080` 检测包含零byte；非零返回0，未含零则两地址各加4继续。故它在有效的零结尾输入上按 unsigned byte 字典序比较，并非 source 指针相等比较；不同地址的相同内容可以返回0。未认证此 helper 的来源版本或完整 libc，未做全函数导出。厂商语义继承只读 ap01thead2.sinc 的 lrbu 规则，并独立核原字段；不修改模型，不把模型等同硬件运行证明。

## 两条查找接入与 PNG normal key

头候选通过已有 OrderNode.word0→TreeNode.word10 取得 payload。`ba8c` 读取 cache+10，`ba8e` a0=payload，a1 保留调用者 key，`ba92` 间接调，`ba94` 返回非零才 fallback；0沿旧直接返回entry路径，无链改写。

树查询 `a00ea832` 保存 key 到 s3、树描述符到 s2；每次候选读取 tree+4 comparator、TreeNode+10 payload，调用 `(key,payload)`。返回0即返回该 TreeNode；负数走 node+4，正数走 node+8；NULL候选返回NULL。这里只恢复查询的比较接口和方向，不恢复树平衡或所有插入。

上述已核比较规则的零值关系对调参数保持不变：class不同均非零；同class0只source相等为0；同class1只内容相同为0；同class其他非零值均0。所以两个入口默认使用同一个匹配条件，反向只影响非零符号。头失败后的树 miss/hit及顺序操作均继承 A34/A36。

已知 PNG normal 协议直接接 A23/A30：key+0=Pixel+c data_size、key+4=session.source、key+8=session.source_class。class0 source是借用ROM descriptor，匹配依赖这个地址及class，不依赖压缩内容、像素size或Pixel身份。缓存插入时既有copy把 key复制至payload，class0保留原source；class1既有 wrapper把payload+4换成字符串副本，比较仍按内容，故复制不会破坏该匹配条件。以上不新增 source复制/析构恢复，payload Pixel等 owner和失效/cleanup次序均沿用 A23/A27。
