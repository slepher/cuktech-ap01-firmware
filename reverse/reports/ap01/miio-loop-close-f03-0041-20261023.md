## 注册链与两个不同的 walker/consumer

`a005a7f0/a802/a806`使loop+8/+c构成以loop+8为哨兵的双链表。`a009d106(loop,timer)`的`a009d112..d128`将timer+10插入该链尾：

```c
node = (char *)timer + 0x10;
node->next = (char *)loop + 8;
node->prev = word(loop, 0x0c);
word(node->prev, 0) = node;
word(loop, 0x0c) = node;
```

指针均32位；timer+8写byte13。`data@0`与`close_cb@c`、业务到期callback@30是三个独立字段。初始化清+28/+30等，**不初始化data，也不初始化close_cb@c**。本轮不从未写字段推断RAM初值。

从既有链引用定位到容器内一个真实walker：`a005a972`读loop+8到s4，s6=16，`a005a9d4..a9e8`读`byte(node-8)`，仅等于16时调用`a009e840(node-10)`，然后`node=word(node,0)`，直到哨兵s2。它位于初始化错误清理路径。type13的9428不会命中这个type16条件；此walker不能作为共享timer正常关闭证据，亦不能据此断言所有其他阶段不存在walker。`a009e840`内部在本任务不展开。

另一个已知consumer是pending单链表，不是注册双链表：`a005c166/c16a`读取并清loop+d4；`c802`在调用`a009f524`前保存handle+28到s5，返回后取保存next继续。两种链必须分开：登记到loop+8并不会自动进入loop+d4。需要一条实际close/入队边，当前对9428没有建立。

本轮有界定位只查既存完整容器汇编中的直接loop基址+8/+c引用、已知初始化/退出链、保存记录给出的caller和该caller的直接返回后继。没有全ROM泛扫，没有把这种直接基址引用检索解释为别名/间接访问全集。

## type13 的条件 close 完整连接

以下假定外部确实调用`a009fb96(timer, close_cb)`并满足其正常flags前置；这是假设入口合同，**不是声称9428存在该调用**。

| 函数或局部 | ABI、字段和顺序 |
| --- | --- |
| `a009fb96` | a0=handle，a1=关闭callback。正常路径要求原flags@2c低2位为0；`fbc2/fbc6`写flags OR1，`fbc8`读byte type，`fbcc`写word callback到+c，s2保存handle。异常assert路径不作新保证。 |
| type13分支 | `fc4e: c.li a5,13`；`fc50: beq a4,a5,+144`到`fd94`；`fd94/fd98`的AUIPC/JALR目标为`a01b2b5c`，a0仍是原handle。`fd9c: c.j -be`到`fcde`。stop内部沿F02，不重解heap。 |
| `fcde/fce0` | a0重取s2，调用`a009c228(handle)`；`fce4`跳返回片段`a00a0026..0038`。未确认业务返回状态，不能命名为成功码。 |
| `a009c228` | 正常前置bit0=1、bit1=0；`c256..c25e`执行`h->next_pending=loop->pending_head; loop->pending_head=h`，字段+28/+d4。不读取data或callback。 |
| `a009f524` | a0=handle，正常前置bit0=1、bit1=0；写bit1，读byte type。`f580..f58e`的`(1u<<type)&0x275e`对13非0，转`f8b6`共用尾部。无需其他type内部清理。 |
| 共用尾部 | 处理bit3；bit0已1，所以其`f8c8`跳过该尾部loop计数减一。`f8d6/f8da`调用摘链helper(h+10)；再`f8de`读h+c；NULL直接返回，非NULL在`f8e4/f8e6`以a0=h调用。返回值未消费。 |
| `a0098b4a` | a0=node；读取node+4的prev、node+0的next；`prev->next=next`；再读node+4；`next->prev=prev`。不清node、不自环初始化、不读h+0。无已确认业务返回值。 |

可定位关键原编码：

| 地址 | 字节 | 区分作用 |
| --- | --- | --- |
| a009fc50 | `6302f714` | type13条件到fd94 |
| a009fd94 / fd98 | `97301100` / `e78080dc` | 配对目标a01b2b5c |
| a009fd9c | `89b7` | 回共用入队fcde |
| a009f588 | `9387e775` | 结合前一C.LUI构成0x275e |
| a009f58e | `63940732` | 命中mask到f8b6 |
| a009f8d6 / f8da | `13850401` / `ef900fa7` | 参数h+10，调用a0098b4a |
| a009f8de / f8e4 / f8e6 | `dc44` / `2685` / `8297` | 从+c取关闭callback，以h为a0间接调用 |
| a0098b54 / a0098b58 | `1cc3` / `d8c3` | 两个邻接节点指针回写 |

```c
// 普通flags前置成立、type==13的条件路径。
close_timer13(h, cb) {
    h->flags |= 1;
    h->close_cb = cb;                // +0c，32位
    stop_a01b2b5c(h);               // 活动状态/heap合同沿F02
    h->next_pending = h->loop->pending_head;
    h->loop->pending_head = h;
}
// 必须另有一次已知consumer进入，不能从close返回补造。
finish_timer13(h) {
    h->flags |= 2;                  // 正常前置：bit0=1、bit1=0
    if (h->flags & 8) {
        h->flags &= ~8u;
        // 本路径bit0为1，跳过共用尾部的计数减一。
    }
    Node *node = (char *)h + 0x10;
    Node *prev = word(node, 4);
    Node *next = word(node, 0);
    word(prev, 0) = next;
    prev = word(node, 4);           // 保留helper的重读
    word(next, 4) = prev;
    cb = h->close_cb;               // 摘链之后才读
    if (cb != NULL) cb(h);          // a0不是h->data
}
```

关闭dispatcher没有自动选用业务callback@30，也没有将data作为关闭callback参数。已核type13分支、入队、完成共用尾部和摘链helper没有直接free(data)或清h+0。未展开stop的heap内部不能被纳入“所有callee绝无data访问”的结论；这里沿F02的stop合同，更不把stop当最终free。

## 容器退出与新调用者前沿

F01/F02已经接受`a005c9ea..ca99`只显式控制9480、9228、9894和两个fd。本轮再核到`cad0`返回。此前`a005c83a`将s1改成字符串基址，故不能把退出阶段的s1继续当loop。已验收pending消费位于此前；没有尾部登记后自动回消费的局部边，沿C07/C08的限定结论。

保留记录给出其caller `a005cc1e`。原字节现在确定：

- caller `a005cc60`零化`[s0-0x240, s0-0x240+0x200)`；`a005cebe`传a1=s0-314，`cec2`传a0=s0-240，`cec6`直接调用`a005a736`。因此本loop是caller栈中512 B区域，不是shared timer 9428，不是容器+14的另外动态分配对象。
- `a005ceca`读取`word(s0-314)`到a0，`cece`调用`a0081554`。这是另一对象参数，没有直接把loop地址传过去。该事实不排除该callee经全局或回调取得loop别名。
- 该调用正常返回后，`ced2..ceda`读byte标志。非0跳`ee9a`，在`eea6/eeb6`最终跳`ccfc`；零分支日志后`cf02`置返回a0=0，`cf04`跳`ccfc`。`ccfc..cd34`恢复寄存器、sp加400并返回。可见的这些局部后继没有调用walker、close或pending消费者；不能覆盖它们调用的日志/其他callee内部。

为把这个断边落到真实指令，展开`a0081554..1645`。它保存输入到s1，访问该对象+2c0/+2c4/+2cc等资源，清理若干字段；`a00815e8`读取word(obj+2b8)，非0则取a1=word(obj+2b0)，a0=obj，`a00815f4`调用这个间接callback。随后`a00815f6..1600`将obj+2b0的值和obj先后交`a008ab8a`，沿C03/C04已验收释放封装合同；未再解allocator。callback指针的安装者/真实身份未在本轮建立，故不能断言这条间接边不会关闭timer/loop。其他资源callee内部继续是明确边界，不扩完整对象系统。

这回答了“容器释放次序”的可证部分：loop存储在caller栈上，`a005a736`返回后caller先调用另一对象的清理，再有明确caller返回路径；该栈存储不会由handle dispatcher自动free。没有证明loop全体handle已完成close才回收栈，也没有证明相反的运行时结果。动态loop内部对象、静态timer与动态请求是三种不同所有权。

## 请求/data 两种正常静态状态

F02已接受的请求布局仍为8 B：kind byte@0、value word@4；timer.data@0，业务callback@30，关闭callback@c。

1. **业务callback已完成且data=0：** `a00a0cd0`释放保存的请求，`cd4`随后清timer.data。此后若外部真的提交type13 close并有consumer机会，上述条件关闭路径摘注册节点、按+c决定是否回调；它自身没有data要归还。能否实际发生该close仍缺入口边。
2. **正常提交已成功，业务callback尚未消费，请求仍挂data：** 到期消费若先发生，仍由`a00a0bd8`释放并清data。若讨论最终close先发生的静态情况，type13 close只用+c，未自动用+30处理请求；需要真实close调用及其+c callback才能判断归还责任。当前9428没有找到这种调用/关闭callback身份，因此此状态的退出归还**未知**。没有构造重复提交、异常start或时序实验，也不把该未知写成泄漏或缺陷结论。

注册链只记录handle，不拥有其data的已证实释放动作；generic finish摘链后允许业务关闭callback决定额外资源清理。静态9428本身没有由上述路径free，动态8 B请求的释放与否不能用“handle已close”替代。
