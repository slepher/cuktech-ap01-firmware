# 0031 独立 OTA 限制审查与资源恢复

目标：修正独立更新服务与某个固件包的长度、模块位置、入口和脚本文本绑定的问题，保留真实容量、设备兼容性、认证、文件完整性、非活动槽写入及提交检查。最终把模块放到原更新包之后、7 MiB 槽容量之内，原版所有 GIF 及其描述符逐字节保留。仅在完整离线升级验证通过后更新实机。

## 已确认限制

已安装 A 包的适配器在 `ota_0031.c` 固定 `IMAGE_LEN=6804520`、`MAN_OFF=0x1f9640`，要求来包头部 256 字节一致、固定模块清单与入口、启动脚本含指定字符串。这些限制来自模拟候选构建，不是独立更新传输协议的要求。HTTP 核心本已支持变长 Content-Length，最大 7 MiB。

迁移必须先安装同长度、同旧模块位置且能被旧接收器接受的过渡包，再由过渡服务接收扩容包。最终模块只验证自身清单用于启动和取认证密钥；来包不要求包含本模块、固定入口或启动文本，因此认证调用者也可明确安装兼容的原厂包。原厂包将不再提供独立服务，工具必须在操作前标明这一结果。

## 接收规则

新服务按照每次请求的实际长度接收，长度上限为 7 MiB；包头、型号标记、文件尾恢复记录必须完整存在。验证 BFNP/FCFG/PCFG、头 CRC、同板 Flash/时钟配置及安全启动模式、合理的原生代码长度和入口；不再比较整个 256 字节头。型号按本项目已定位的 0031 镜像标记验证，不能据此宣称支持任意芯片或任意布局固件。验证尾部声明总长度、整个文件 CRC 与传输 CRC；使用原厂写入器写非活动槽，再由原厂读回校验后提交。CRC 是完整性检查，不是固件签名。

未认证、畸形/重复请求头、超容量、超时、截断、CRC 错误、写入失败均拒绝提交；提交结果不确定时保留禁止重试状态。成功后关闭写入句柄只执行一次，避免当前成功路径重复关闭。回复传输失败仍记录已提交状态，不自动重复安装；电脑通过健康检查与原厂运行时间确认是否重新启动。

按用户明确的使用方式，两种 OTA 均人工触发，顺序执行，不会同时启动。跨通道共享锁不是本次部署前提，不为此禁用传统 OTA。HTTP 服务内部仍拒绝重复写事务；尚未验证跨通道并发，不宣称支持该用法。

## 构建与验证要求

保持旧候选构建及原证据可校验，不改历史镜像或清单。当前 HTTP 扩容版从固定 SHA256 的原件重建，只允许启动入口、rcS、ROMFS 校验及槽尾追加改变；保留原启动头、PEC、传统 OTA 入口、原版资源及描述符。扩容包移动尾部恢复记录并重算长度/CRC，不修改分区表或 Boot2。增加扩容格式的显式验证，未知格式继续拒绝。

先运行协议故障测试、变长镜像校验负向测试，再从真实旧 A 包出发，模拟 A→过渡包→扩容包→不同长度扩容包，逐次核对真实写入后的同一份 NOR、活动槽变化、保护区不变和复启后通道可用。容量检查与模拟运行不能替代实机 Boot2；最终实机更新单次发送、持续记录，任何验证失败均不继续刷写。

首轮离线验证已完成；实机差异和后续修正见下文，不能仅用模拟通过声明完成。

## 实机发现与修正

首轮 v3 完成模拟往返和资源检查后，向旧 A 服务仅发送一次兼容包。旧服务返回 HTTP 500 / body / writer / bytes=0；未提交、未切槽，设备运行时间继续递增，米家仍 idle。该结果不能区分旧适配器的首块包头比对拒绝与原厂写函数失败，不能声称已证明唯一故障原因。

代码审查同时发现旧实现直接读取 `0x9ffff000` 作运行时包头比较。这个地址来自离线文件映射，不能由模拟器映射行为推导实机包头可读性。v4 将固定原件的参考板型头嵌入模块只读区，验证不再读取该运行时地址。回归测试在启动后故意把模拟器该映射改为无效数据，要求新接收器仍可完整校验、安装并复启。

旧服务已拒绝兼容包，不能重复同一独立更新尝试。修复路线调整为由旧 A 保留的米家 OTA 入口安装 v4 过渡接收器，确认在线后再由独立 OTA 安装原 GIF 扩容包。新接收器所在包会让原厂云升级分发入口返回 busy，以排除双写；米家通信/查询保留。尚未实现允许两种更新器交替工作的共享互斥锁，不能宣称两种更新入口同时可用。

## 最终实现与离线验收

最终包 `roms/0031/candidates/ota-channel-tail-0031-v3.bin`，6,814,248 字节，SHA256 `73963a0e6bd94096819918626e701996ce97269d5514d64073bbc34c25fb92e0`；服务标识为 `ap01-ota/2r2-tail`。槽内余量为 525,784 字节。过渡包 `ota-channel-bridge-0031-v3.bin` 保持原长，SHA256 `da901f9c1257c27c895a285e7b429a5e166d9a1fa4d4135168e71216ce445657`，服务标识为 `ap01-ota/2r2-bridge`。

扩容包原件主体仅允许启动任务入口、rcS、ROMFS 校验、已核实的云升级分发补丁，以及原生映像跨度字段 0x84 与头 CRC 改变；主体之后追加模块并移动尾记录，所有其他原件字节均由构建器逐字节核对。原 GIF 385,834 字节、320×240、41 帧及描述符完全相同，GIF SHA256 `5e656788665f7f0022b0b5500d569a8aae07f4a46b080d033b3cacfa4abc940d`。没有修改分区表或 Boot2。0x84 的原生跨度字段扩展覆盖新增可执行区，不能把模拟器启动等同于物理 Boot2 验收。

保留认证、精确接收长度、7 MiB 上限、已支持板型/原始包格式、头 CRC、型号、传输 CRC、尾部总长度/CRC、原厂槽内读回校验、非活动槽和提交未知状态保护。取消来包与运行包等长、整个头逐字节相等、固定模块位置/入口和固定启动文本要求。该接收器仍只支持已验证的 AP01 0031 原始包布局，不宣称支持任意板型或压缩格式。

离线验收：42 项协议故障检查、22 项镜像格式/容量/兼容性检查、23 项构建/资源/篡改检查、20 项槽表/保护区检查及 4 项发送工具场景通过。发送工具检查成功、回复丢失、明确拒绝及只检查模式；已有任务记录禁止重复发送。协议与镜像宿主检查使用 ASan/UBSan。较早的 v3 模拟证据保留，最终 v4 重新执行 A→过渡→扩容→加长→缩短→同一 NOR 复启，每步独立验证 CRC、age、活动槽及保护区域；新接收器测试在启动后刻意破坏 0x9ffff000 模拟映射仍通过。云入口实际执行返回 -16 且未进入原处理函数；成功新接收器每次只关闭一次 Flash 句柄。

测试清单和指纹保存在 Git 忽略的 `evidence/private/ota-expansion-20261018/validation-summary-v4.json`，详细原始报告、合成 NOR、编译文件、密钥和实机任务分别保留，不覆盖历史构建清单。没有使用 delegate 技能或重新启动子代理。

## 用户要求优先恢复原厂状态

用户要求先救回设备，日志开发暂停；新增日志代码没有刷入设备。恢复目标改为固定 SHA256 的未经修改原版 0031，撤去过渡服务及原厂 OTA 永久 busy 补丁，不再部署扩容候选。

先使用已冻结的 v4 过渡接收器在模拟中单次恢复原件，报告 `bridge-to-stock-recovery.json`；独立验证报告 `verify-bridge-to-stock-recovery.json` 核对新槽逐字节等于原件、切槽及受保护区，均通过。模拟未执行物理 Boot2，此限制不变。

随后通过设备现有独立入口单次发送原件，任务 `restore-stock-device-task.json`。恢复连接最终超时，没有捕获成功 HTTP 回执；未重发。独立的重启后观察显示实机重新上线米家，版本 `1.0.2_0031`，运行时间从 1030 秒重新计数并稳定递增；原补丁端口 18080 返回 ConnectionRefused。**用户确认“屏幕、GIF 和旋钮都正常”。** 任务最终为 `stock_runtime_observed`，恢复后的接口观察与用户实际操作共同确认恢复正常运行，不再继续功能升级。

传统入口诊断不包含固件地址，不触发第二次刷写：云端空参数请求由云层返回 `ota bucket not permit`，不能用于证明设备处理器状态；局域网认证空参数请求实际返回设备错误 `-30020 / service not available.`，不再是固定 busy 补丁导致的无响应。这证明原厂处理路径可以返回原生响应，不代表已实际完成一轮云 OTA。证据 `restored-traditional-ota-probe.json`、`restored-local-ota-probe.json`；恢复脚本及观察均保存在上述私有证据目录。


## 统一 18080 的后续离线修正

2026-10-18 后续已将诊断合并到 OTA 的 HTTP 18080，删除独立 18081 监听器。监听与请求执行拆开，四个有界 TASK 分别处理连接；原生回归确认未完成上传期间日志、状态、Flash 读取和命令仍可响应。候选使用 `--mode http`，保留原启动头、GIF、PEC 与传统 OTA 指令，不再使用永久 busy 作为发布方案。验证、协议与已知限制见[统一服务记录](knowledge/0031-network-console.md)。

完整模拟写入和槽提交已有逐字节快照验证；真实 Boot2 未取得，扩容镜像的物理启动尚未验证，因此本轮没有刷设备。不能把原生函数返回成功或模拟新槽一致当成物理启动成功。两种 OTA 按人工顺序使用，跨通道共享锁不再作为部署前提。

后续启动头、PEC、槽尾路径和槽号来源的离线核查见[启动链调查](knowledge/0031-expanded-boot-investigation.md)。失败包改变了头部长度与 PEC 的相对布局，但尚未证明真实 Boot2 如何使用这一关系，不能记为已确定的失败根因或槽尾执行限制。
