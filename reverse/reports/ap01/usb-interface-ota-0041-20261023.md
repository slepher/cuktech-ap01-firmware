# 0041 底座 UART 协议与 MCU OTA 局部合同

2026-10-23。固定原厂 0041 SHA256 `972db4c136c7ed9e24a83c07c1a7fd62040ca018b08ca285216d26b1fee3c6b9`。本轮属于[整 ROM 非开源逆向](whole-rom-0041.md)，不修改正式 ROM，不执行底座升级。这里的 USB interface OTA 是原厂经底座接口更新 MCU 的链路，不能与 AP01 联网更新自身 application 槽混称。

`a00a3df4` 先写阶段，再调用 `a00a3a0e(status,progress)`。后者遍历原厂链表，调用每项的 `(userdata,status,progress)`。`a01b25e8(callback,userdata)` 按 callback 去重，已有项不更新 userdata；未命中则新增。启动阶段注册日志测试回调 `a00a4030`，userdata 为 200。退出按 callback 删除。

多处状态改变后会再次检查当前阶段，只有仍处于预期阶段才发送下一命令。这些检查保留了同步通知可能改变状态的边界，不能重建成无条件连续发送。

## OTA 主流程

`a00a56d4` 仅在传输状态 0 时开始；否则设 OTA 阶段 1 并返回。更新位图没有 bit1/bit0 时只记录“不需要 OTA”。有任务时选择 RAM 头部，清失败码、设置阶段 2、替换响应函数，并提交 D0 命令和 16 B 参数。D0 参数源依 selector 为 `a026ad80 / a026ad90`。

响应处理 `a00a5810(cmd,len,payload)` 的局部合同如下。D0、D2、D4、D5 分支先复制 1 B 状态；它们是否一定有至少 1 B 输入仍依赖上游解析合同。

| 响应与当前阶段 | 成功路径 | 失败或特殊路径 |
| --- | --- | --- |
| D0，阶段2 | 状态0 → 阶段3、索引0，取第一块，再发 D2 | 状态非0：失败4；无数据项：失败5 |
| D2，阶段3 | 状态0 → 下一块 D2；遍历结束 → 阶段6、发 D4 | 状态非0：失败6 |
| D4，阶段6，selector1 | 若 bit0 仍待更新，清 bit1，设权重25并重新开始 selector0；否则退出 | 状态非0：失败9 |
| D4，阶段6，selector0 | 阶段4、索引0，取块并发 D3 读回 | 无数据项：失败5 |
| D3，阶段4 | 长度34、地址编号匹配、回读内容与当前16/32 B ROM块相同 → 下一块 D3；结束 → 阶段5、发 D1 | 任一不符：失败7 |
| D1，阶段5 | 长度7，响应中的某 u16 与应用头部 `+0x0a` 相同 → 阶段7、发 D5 | 长度/字段不符：失败8；不把这个字段直接命名为版本或校验和 |
| D5，阶段7 | 状态0 → 退出 | 状态非0：失败10 |
| 0x23 事件 | 控制 byte 尚非2时改为2并失败1 | 已为2则直接返回 |
| 0x24 事件 | `a01915bc` 尝试取排队命令 | 不等同某一 OTA 阶段成功 |
| 其他不匹配响应/阶段 | 失败2 | 未知命令有独立直接返回分支，不能统一成失败 |

`a00a3e54` 从当前头部 `+0x0e` 取 u16 项目数。ROM 数据从头部后 `0x12 + index*16` 读取；通常一次16 B，存在下一项时合并为32 B。selector1 的地址编号为 index，selector0 为 index+0x180。型号 byte 为2且 selector1 时本函数直接返回0；这是局部不支持分支，不代表所有型号2的升级均被禁用。

`a00a468e` 将地址编号和16/32 B数据组成 D2。`a00a41ba` 发送 D3，长度2，内容为地址编号。进度由阶段基值加 `index*权重/项目数` 计算并截成 byte；通知只在变化时发出。完整进度含多部分更新，不能把一次块序号直接当整机更新百分比。

`a00a4762(error)` 存储失败码后调用 `a00a4708`。退出包括 UI interface deinit、底座动态状态释放、恢复普通响应函数、控制参数恢复、阶段置0及撤销测试回调。**阶段0表示该流程已退出；应同时检查失败码，不能把 idle 当升级成功。**

## 传输、排队与帧格式

`a01951e2` 接收的最小命令描述符为 `{u8 cmd; u8 len; padding; pointer payload @+4}`。空闲时将 cmd/len 保存到活动区，len 为1..45才复制 payload，然后进入发送处理。忙时检查四个48 B槽：相同 cmd、len、payload 的项不重复排队；否则取第一个空槽，全部占用时直接返回。该函数未返回显式“入队成功”状态，调用者不能仅凭函数返回当成功。

`a01915bc` 按固定槽顺序取第一个非空项，只有活动传输空闲才搬入活动区、启动发送并清该槽。它不是按到达序号维护的独立 FIFO。注册/发送相关低层复制函数的反编译有时少打印第三参数；已按 `a0195224 / a0195270 / a01952c4` 等汇编核对实际 a2 长度，不沿用缺参数的伪 C 声明。

`a01a4ff8` 组织帧：起始 A5，随后一个初始为0的字节；CRC 先处理这个字节，再处理 cmd、len 和 payload；CRC 低字节在前附加。主体中的 A5、5A、AA 用前置 AA 转义，结束追加 5A。编码存在写入索引超过0x5e后的提前返回路径，不能假设任意45 B payload均形成完整尾标记；当前 OTA 数据块发送长度18/34仍需按真实内容单独验证。缓冲界限的完整审计未完成。

`a00ee96c` 处理底层部分写：只有正返回才增加发送游标，游标达到帧长才置传输状态2并清发送计数。非正写入不会在此宣称发送完成。重试/超时调度仍需继续追踪。

`a00a8330` 是 UART poll 回调，先逐字节读取到100 B环形区，再解帧/转义。`a00ee934` 追加解码字节，计数超过47时清计数及解析阶段。结束标记到来后，长度大于4才调用 CRC；CRC 匹配且当前传输状态2、响应cmd等于活动cmd时，将响应交给 `62fcb6c0`，再发一次0x24事件用于继续队列。CRC正确但cmd不匹配不构成该活动命令完成。

## CRC：已纠正一处反编译结果

`a00ee8fc` 的伪代码把函数推成 void，删除了 CRC 计算，只剩循环。这与真实汇编不符：`th.lrbu` 取字节、`th.lrhu` 访问 `a056d058` 的表，a0 更新为左移/XOR后的16位值并返回，调用者使用该结果。

ROM 中256项 u16表完整匹配多项式 `0x1021`。从汇编和表恢复的正长度递推为：`crc = ((crc << 8) ^ table[(crc >> 8) ^ byte]) & 0xffff`。发送路径 initial=0；宿主表驱动与独立逐位实现的12组比较通过，`123456789` 的初始0结果为 `0x31c3`。这些是静态恢复算法的宿主验证，不是原厂函数的运行向量验收。原循环是 do/while，长度0仍会进入一次，验证工具明确拒绝将空输入按常规 CRC 库语义代替。

`a00a45d8` 将18 B头部复制到RAM。型号1选择 TA1208 数据，型号2选择 TA1408；公共 selector1 头部两者均取同一位置。

| --- | --- | --- | ---: | ---: |
| `a026adb0` | `0x26bdb0` | `46 49 54 01` | 3072 | 49152 B |
| `a0276dc4` | `0x277dc4` | `62 75 70 01` | 2664 | 42624 B |
