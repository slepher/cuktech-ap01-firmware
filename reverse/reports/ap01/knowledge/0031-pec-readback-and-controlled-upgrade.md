# 0031 PEC 读保护与独立 OTA 对照（2026-10-18）

本轮先用现有诊断接口采集，再以已经实机启动的同一份 `ap01-diag/gif1` 做单次独立 OTA 对照。没有部署扩容包，没有恢复原版 GIF。私有原始记录在 `evidence/private/diagnostic-gif-20261018/`。

## PEC 读回差异的实证

FW1 运行时，Flash TrustZone 控制字 `0x20005280=0x021ffff5`：区域 0 使能、锁定，权限掩码为 `0x5`。区域字 `0x20005288=0x1a221a34`，MSB 为 0，对应物理 `[0x688800,0x68d400)`。本地 SDK 的 `TZC_SEC_ADV_AUTH_GRP_*` 定义确认 bit 0/2 是两组 IBUS、bit 1/3 是两组 DBUS；因此该区允许取指，禁止数据读取。AES 区域的使能和范围另外读取，两者不能混为同一保护。

该区 XIP 数据读取返回重复 `DEADBEEF`。SPI 读取 16 字节、256 字节及偏移后 16 字节均不能取得有效内容；不同请求出现固定前缀与不同填充值。设备返回成功和传输 CRC 正确，不代表取得有效 NOR 内容。实际 RAM 读取函数与原件对应 144 字节一致，REA 核对其关闭 AES、发 SPI 读、恢复状态的路径；调用约定没有发现参数顺序错误。

对照升级后，实际运行 FW2，TrustZone 范围字变为 `0x38a238b4`，对应 `[0xe28800,0xe2d400)`；权限/锁定不变。FW1 的同一物理位置恢复为原包密文，FW2 则出现此前的无效读数。单连接导出现在非活动的 FW1，其前 **6,804,520 字节逐字节等于正式诊断包**，SHA256 `aafe8d1759c65a3423aee6a126c008a6336473a74cf6945669a7158746ca86a9`，包括全部 PEC 字节。

这组同一设备、同一物理内容、切槽前后保护状态相反的对照，确认先前 PEC 差异来自活动槽读保护，不是该区域实际被改坏，也不是可信的明文导出。当前 FLASH 接口没有识别此类被抑制的读取，不应继续把它的成功响应直接称为原始物理备份。

## 实际升级路径

`control-same-diag-v1/task.json` 持久标记禁止重发。升级对象仍为已安装、实机启动过的同一正式包。执行前核对 DID、运行 build、实际 FW1、目标 FW2、两表 CRC、年龄 6、冻结源码指纹及既有离线完整写入/复启证据。该对照不以版本字符串相同作为成功标准。

设备持久日志按顺序记录 `begin → flash_open → progress → image_valid → readback → slot_commit_start → slot_commit_return → response_committed → reboot_request → boot`。HTTP 200 回执确认 6,804,520 字节；原厂读回与提交返回 0。复位前最后日志为 ms 2450108，重启后的 boot 为 ms 673，BootROM 实际 XIP 偏移从 `0x11000` 变为 `0x7b1000`，复位原因 4。物理表由 E000 年龄 6 / FW1、F000 年龄 5 / FW2，变为 E000 年龄 6 / FW1、F000 年龄 7 / FW2。环境 current/update 和 RAM FW 条目均与实际 FW2/FW1 相符。

因此当前诊断接收器对这份已知可启动镜像，确实完成独立 OTA 写入、提交、软复位及新槽应用启动。它不证明旧 bridge 接收器上传旧扩容包时走完了相同路径，也不证明旧扩容头部可被实际 Boot2 接受。

对照时 STATUS 的 5 秒查询超时，直到重启后才成功；米家期间仍在线。观察程序按 STATUS 后 LOGS 的顺序查询，STATUS 超时后没有独立发 LOGS，不能据此声称所有诊断通道都阻塞，亦不能声称实机“上传时查询”要求已经通过。此项仍需单独验证。

## 日志字段修正要求

实机表的第一个条目是 Boot2，FW 在后。已部署 gif1 的 OTA 日志误把固定 `table[18]` 作为 `table_active`，实际读到了 Boot2 的活动字段；STATUS 按条目名查找 FW，结果正确。本次日志中 `table_active=0` 不能用于推翻 STATUS、物理表和 XIP 所确认的 FW2。源码应在有界条目数内查找类型 0、名字 `FW` 的条目，并以真实 Boot2 在前 / FW 在后的表回归；不通过重新刷设备掩盖历史日志含义。

## 旧扩容根因边界

旧 tail-v4 模块仍在 FW2 槽尾且逐字节匹配，证明其载荷曾写入。此次已确认 PEC 读保护，并确认当前已知包的实际升级链。旧扩容失败当次的头部与表已被恢复覆盖，旧接收器没有持久复位日志；实际 Boot2 仍只有加密正文。当前保留 RAM 中发现可解码的 Flash 辅助代码，但尚未证明其包含 Boot2 主启动逻辑。不得把这些代码直接冒充完整 Boot2 明文。

因此仍不能唯一裁定旧失败发生在复位前、Boot2 选槽/PEC 处理或应用初始化。尤其不能将“扩展头部长度改变了 PEC 对齐关系”升级成已经观察到的 Boot2 失败原因。原版 GIF 恢复继续等待该证据缺口解决。
