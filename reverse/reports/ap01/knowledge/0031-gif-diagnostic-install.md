## 已可查询的信息

18080 保留认证 HTTP OTA、健康、日志与诊断 Upgrade；传统 OTA 入口未改。STATUS 新增：

- `running.xip_offset`：直接调用实际 BootROM 表第 329 项取得控制器偏移；原始值与规范化槽号均保留。
- `physical_tables`：从 `0xe000/0xf000` 分别读取 596 字节，独立校验头/条目 CRC，输出年龄及 FW 活动槽，不只读 RAM 副本。
- `reset.native_code`：原厂启动阶段保存于 `0x62fc5c5c` 的复位原因。持久启动日志也保存 `xip_offset/reset_reason`。

不要将模拟器返回的槽基址与实机返回的“槽基址 + 0x1000”混为一谈。查询同时报告原始偏移，不能只据环境变量声称实际运行槽。

## 实机采集与读取视图

已导出启动区及槽表的前 64 KiB，两槽各 7 MiB 的原厂 VFS 视图、启动日志、空 crash 分区、原厂命令列表，以及部分实际 BootROM 函数代码。没有成功取得可称为完整原始 NOR 的 16 MiB 导出。

通过 NSH `cat /dev/fw1` 的单连接导出，正式包在 PEC 正文之前的所有字节、PEC 之后到包尾的字节均与本地候选一致；新增诊断代码全部位于已核对区域。PEC 正文在原厂 VFS 和当前 FLASH 调用链中呈现不同视图，均不能未经解释就等同于原安装包密文字节。**尚未据此核验整个物理包的原始 SHA256，不把差异直接认定为损坏或已正确解密的代码。**

连续 FLASH 短连接导出出现超时；单独首 64 KiB、4 KiB 分块小范围、单连接完整固件槽导出均已有成功记录。缩小分块未解决所有连续导出超时，故不能宣称这是 64 KiB 容量限制或已确认的 TCP 连接数限制。客户端增加 `--chunk-bytes` 用于诊断，默认保持 64 KiB。超时报告与不完整文件均保留，不算完整备份。

实际 Boot2 头的配置字为 `0x72cf0104`，代码偏移 `0x2000`，跨度 `0x92f0`；正文有加密标记且高熵。目前没有 Boot2 明文，不能对密文作可信反编译。读取了 Flash AES 区域的范围/使能字段，没有读取密钥或更改硬件配置。当前唯一使能区间覆盖运行槽的 PEC 正文。

## 关于旧扩容未生效的新证据

`device-fw2-vfs-view.bin` 的原版包长度范围内，逐字节等于原版 0031。它在文件偏移 `0x67e000` 仍保留旧 tail-v4 模块：6,641 字节逐字节等于历史载荷，SHA256 `1115b36cdd9eb38da5e98efa5dbdac5e7dd514156a2111fdaca2c7e7bdf29a05`，自描述总包长仍为 6,814,248。结果见 `old-tail-residue-verification.json`。

这证明旧扩容载荷确实到达了 FW2，进一步排除了“因固定原包长度而完全未接收/未写入扩容载荷”的解释。当前 FW2 的头部已被后续原版恢复覆盖，不能把它当成失败当时的头部。crash 分区未发现异常记录。尚无失败当次的复位/选槽轨迹，也没有 Boot2 明文；不能仅凭残留、头部布局相关性或当前 AES 区间唯一认定失败发生在 Boot2 或 PEC。

后续保持当前可启动诊断版及传统 OTA，先解释 Flash 各读取视图和保护状态，再决定是否需要补充诊断功能。不会为制造根因证据而直接重刷已知未生效的扩容包。
