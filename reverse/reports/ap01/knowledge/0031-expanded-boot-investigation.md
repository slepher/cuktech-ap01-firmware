## 启动头与 PEC：确认的差异

用独立只读脚本 `tooling/scripts/audit-ota-boot-layout-0031.py` 生成 `boot-layout-audit-v2.json`。它不调用候选构建器，也不输出认证密钥。

| 字段或位置 | 原版 | 失败 tail-v4 | 当前 HTTP v2 |
| --- | --- | --- | --- |
| 头部 `0x84` 的长度 | `0x6764f0` | `0x67ea00` | `0x6764f0` |
| `0x1000 + 长度` | `0x6774f0` | `0x67fa00` | `0x6774f0` |
| 上述末端向上对齐到 2 KiB | `0x677800` | `0x680000` | `0x677800` |
| 实际 `PEC:` 文件位置 | `0x677800` | `0x677800` | `0x677800` |
| 256 字节启动头与原版一致 | 是 | 否 | 是 |
| 头 CRC、文件尾长度及 CRC | 均有效 | 均有效 | 均有效 |

失败包把声明的原生镜像范围扩展到了 PEC 及新增模块之后，PEC 没有移动。原版的“代码末端对齐后即 PEC”关系因此被改变；当前候选恢复了这个关系。这是直接字节证据，**还不是 Boot2 必然依此查找 PEC 的证据**。不能因此擅自搬移 PEC、重编码其内容或认定头部长度就是 XIP 映射上限。

原件调用 PEC 的应用指令使用固定基址 `0xa0676800`（文件偏移 `0x677800`）。例：`0xa002a336` 加载基址，读取 `+0x30` 相对入口，再于 `0xa002a348` 间接调用；保存于 `pec-call-0031.asm`。这证明该应用调用方不通过 `0x84` 动态定位 PEC，不能据此推导 Boot2 的内部处理。

PEC 从 `+0x1000` 起的内容高熵，直接按明文指令反汇编并不形成可信程序；实际保护/解码流程未取得。现有 QEMU 的 PEC API 替换模型不实现该流程。

两份扩容包的模块自描述长度、偏移、代码 CRC、清单 CRC、builtin 入口与模块入口均相符。入口均为 `0xa067d100`，位于槽内追加的代码区。当前候选距离 7 MiB 槽上限仍有 `0x7e978` 字节；容量本身不能证明启动兼容性。

## 长度字段不能直接等同于映射边界

本地 Bouffalo SDK 固定提交 `41bf338a57be53919d99f6c6715a96100428c97d` 仅作为通用实现参考，**不是设备上的 AP01 Boot2**。相关源文件已冻结为 `sdk-reference-bflb_port_boot2.c` 与 `sdk-reference-bflb_sp_media_boot.c`。

该参考实现用 `img_len_cnt` 做非零检查，并在启用 hash 校验时决定 hash 范围；`hal_boot2_set_cache()` 向 `bflb_flash_set_cache()` 传的是 Flash 偏移与缓存配置，没有传入该长度。三份镜像的头部 hash-ignore 位均为 1、首 hash 字为 `0xdeadbeef`。设备实际 eFuse、AP01 定制 Boot2 和 PEC 初始化规则仍未知，不能据参考源码宣布实机一定忽略 hash，也不能宣称保留原长度就一定无法执行尾部代码。

## 槽尾执行路径：已经运行到哪里

新增 `tail-startup-path-v1.json`、`http-startup-path-v1.json`，对两份冻结镜像分别运行原生应用代码并观察断点：

1. 应用入口 `0xa0000000`；
2. 原厂 builtin 分发路径 `0xa0031b98`；
3. 槽尾入口 `0xa067d100`，两者返回地址均为原厂任务启动路径的 `0xa0033744`；
4. 失败 tail 包从槽尾调用 `bind`（`0xa003f398`，调用者 `0xa067d37a`），创建服务线程并进入服务函数；
5. 当前 HTTP 包从槽尾调用 `bind`（调用者 `0xa067ec58`），UART 记录 `AP01_HTTP_BOOT listener_pid=30 port=18080`。

两轮均无 guest exception，`provider_calls={}`，未用宿主 socket 替换原生 TCP 函数。它们说明在当前模型提供映射与 PEC API 的条件下，任务启动钩子确实能执行到新增代码，不只是静态推断。

边界：`tooling/scripts/qemu-ap01.c` 直接把整份输入镜像加载到 `0x9ffff000` 的 16 MiB 区域，并在固定 PEC 基址提供替换 API。它不运行 AP01 实际 Boot2，不证明启动头解析、PEC 处理、物理 XIP 配置或真实切槽成功。原先全包探针 v13 在 PEC MMIO 上的字节读取异常，属于模拟探针错误，不作为实机根因。

## 槽表副本编号与 FW 活动槽不能混用

原版函数 `0xa0058f2a` 校验两张分区表并选择较新的有效表；副本编号保存在 `0x62fc8cd4`，选中的表复制到 `0x62fc8cd8`。`partition-init-0031.asm` 保存了原始指令。

随后原厂应用有两种不同的选择依据：

- `0xa00590b4` 至 `0xa00590d6` 依据**副本编号**选择 `ro.boot.current_slot` 环境字符串；`0xa0059168` 至 `0xa0059178` 取其反向值设置 `ro.boot.update_slot`。
- `0xa00590b0` 读 FW 条目的 `activeIndex`，通过玄铁条件搬移指令选择对应的物理地址和容量。

对原件指令的两组交叉输入验证如下。表 CRC 均重算；QEMU 直接加载运行镜像，所以这不是对 Boot2 选槽行为的测试。

| 合成输入 | 原件设置 current_slot | 原件设置 update_slot | 证据 |
| --- | --- | --- | --- |
| 表副本 0 较新、FW active=1 | `/dev/fw1` | `/dev/fw2` | `pt0-active1-path.json` |
| 表副本 1 较新、FW active=0 | `/dev/fw2` | `/dev/fw1` | `pt1-active0-path.json` |

因此，未来诊断必须区分表副本编号、FW 活动字段、环境字符串和实际 XIP 物理偏移。**尚无失败现场槽表，不能断言它们在实机上失配，不能把这项发现写成已确认根因。** 当前诊断已经分别输出环境槽号和 RAM FW 条目；仍不能仅靠这些字段宣称实际运行槽已证实。

## 保留内容与当前结论

独立审计确认当前 HTTP 候选的启动头、PEC、385,834 字节原版 GIF、GIF 描述符及传统 OTA 入口字节均与原件一致。旧 tail 实验包确实修改过传统入口，因此不能拿旧包作为当前保留要求的合格产物。两种 OTA 按用户指定的人工顺序方式使用，不以跨通道共享锁作为本轮部署前提。

针对冻结的本地文件，现有证据排除了镜像超出 7 MiB、头 CRC 错误、尾记录长度/CRC 错误、模块 CRC 错误、入口指向错误这些具体问题；应用启动钩子也在当前模型中得到执行验证。这不是失败现场 Flash 内容的证明。**尚不能区分实际写入/提交未达到预期、Boot2 选择旧槽，以及新槽在 PEC 或应用初始化阶段失败等现场分支。**

离线材料缺少实际 AP01 Boot2 和失败后的物理 Flash/槽表，无法把这些分支唯一归因。后续若有真实 Boot2、启动记录或物理读回，应先核对失败现场的两张表、两槽头部/尾模块及实际 XIP 偏移，再判断哪一分支成立。不能用新的模拟通过覆盖这个证据缺口，也不为取得证据先刷一个未经启动验证的候选。本轮未刷设备，候选继续保持 `physical_boot_verified=false`。

## REA 对原版二进制的复核

使用 REA 6.5.0 / Ghidra 12.1.4，显式指定 `raw-binary`、RV32、文件基址 `0x9ffff000`、入口 `0xa0000000`；原件 SHA256 与上表一致。本次 REA 已实际完成函数分析，不再沿用此前 Windows 不支持该 raw RISC-V 目标的判断。完整 11 条证据保存于 `rea-boot-investigation-v1.evidence.json`（8,640,102 字节）。它是静态分析记录，不是设备执行日志。

### 可确定的结论

原厂 `0xa009b8da` 使用调用者给出的 `offset/length`，读取区间末尾的 4 字节期望 CRC，以 128 字节块计算文件 CRC；需要时还原首字节，成功返回 0。它没有在此函数中执行 Boot2、验证槽尾取指，或把原版 `0x67d428` 当固定包长。证据 `ev_7363c73b0741874e2f368fb8889c450d95675bfd02a38ee657c0b0a0b764a7e0`。

`boardctl(0xff13, path)` 从参数或 `ro.boot.update_slot` 取得目标名称，选择 `/dev/fw1` 或 `/dev/fw2` 对应的序号，更新 FW 条目活动序号和年龄，重算分区表 CRC，擦写另一份分区表。该提交分支不执行新槽，也不包含新固件启动成功确认。证据 `ev_dbd9bb2b61d7461256cc2b5bae280a14ac19e877cf9621172332e7d865fc13a9`；其中被 Ghidra 错误截断的 `0xa0056f10..0xa0056fdf` 用 REA 原始字节证据 `ev_203ebda77c6f5a0c6208079367050c161ad4746ad48acaea90e0a035b2e3a8e5`、`ff13-commit-native.asm` 及此前同一原件的原生提交执行记录交叉核对。

因此，结合冻结 bridge-v4 接收器的返回路径，现场 `HTTP 200 / done / ok / bytes=6814248` 支持的是**接收器已通过文件检查并得到槽提交成功返回**，不支持“新槽启动成功”。本次未生效不能归为“接收器仍强制原包长度所以拒绝扩容包”；也不能从这个响应倒推出 Flash 在重启后一定保留了预期内容。

PEC 固定基址调用的 22 字节由 REA 直接读回，证据 `ev_75f2e4fd473e20b7b7cc8c4c80a142912a7404e8c603e7cd020754faee5f398b`，与此前 GNU 解码一致。启动头长度改变与 PEC 未移动仍是确认的布局差异；REA 没有提供实际 Boot2 如何处理该关系的证据。

### 不能直接采信的反编译结果

Ghidra 通用 RV32 模型没有完整恢复本固件的玄铁扩展指令。启动初始化函数的伪代码在扩展指令处停止；内存复制/清零辅助函数出现错误的 `hasNoReturn` 传播，使若干调用后的真实代码被排除在伪代码外。相关证据为 `ev_499652b3326f95a0530d5d16e49d68979dc20768f960212bd12584cd4d229c4a`、`ev_5acf682e797d738da2214694f60bb0a700f15543919ce8b62072aca83c100492` 和 `ev_6c5bb4891a09051f3fd9c13520c86c672de3a10e9d5afa3114dc7c175e049472`。这些是工具恢复限制，不是设备代码本身不返回或无法启动的证据。

启动头 `0x9ffff084` 与 PEC 基址的自动 xref 查询为空，也不能用来宣布“原件没有相关引用”；现有固定基址调用就是自动 xref 不完整的反例。

### 根因裁定

**确定：上传拒绝不是这次现象的解释，文件校验与槽提交成功返回不等于启动成功。未确定：实际复位是否发生、新槽是否被 Boot2 选择，以及 PEC/应用初始化是否失败。** 这几个分支缺少现场记录，不能仅靠已有应用包静态逆向唯一裁定。此前“复启后仍旧版”的说法应收窄为“提交后查询仍旧版”；没有复位证据时不能擅自把问题定位到 Boot2。

本次 REA 没有得出“必须扩大头部长度才能执行槽尾”或“保留原头部必然启动失败”的结论。当前候选保持原版 GIF、PEC、启动头与传统 OTA；未刷设备。
