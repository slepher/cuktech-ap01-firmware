## 布局和所有权复核

总对象 `62fcb2cc` 的 `+0 array`、`+6 u8 count`、424B item 及 cmd55 零初始化采用已有合同。新增局部布局：

| item 偏移 | 宽度 | 含义/尺寸 |
| --- | --- | --- |
| +00 | u32 | 通知可见 mask，分发结束清零 |
| +0d / +0e | u8 / u8 | 活动状态 / 类型（15h=本分支 CTK） |
| +28 / +2c / +30 | 32位指针 | Dev20B / Port24B / BMS12B |
| +34 / +38 | 32位指针 | Cells24B / Power24B；按日志分析命名 |

五个嵌套字段都是 item 持有。`cmd51` 先发布新类型再清理旧资源；进入15h路径后，按 +28、+2c、+30、+34、+38 顺序检查字段是否为零并申请 20、24、12、24、24 B，原位写回返回值。片段没有整组成功门或回滚。保留空检查的原顺序，不把“清理后通常为零”当成删除检查的理由。

```c
// 顺序视图，不是原源码；load/store 是指定宽度。
if (load8(item+0x0e) != new_type) {
    store8(item+0x0e, new_type);
    cleanup(item);                    // 切CTK和切其他类型均调用
    if (new_type == 0x15) {
        for ((off,n) in [(0x28,20),(0x2c,24),(0x30,12),(0x34,24),(0x38,24)]) {
            if (load32(item+off)==0) store32(item+off, zero_alloc(n));
        }                              // 循环仅压缩表示原来五组展开指令
    }
    changes=0x40;
}
// +10 u16、+12 u8、+0f u8 的比较/变化位继续按原程序更新。
// 有变更时写 mask，同步通知；未变类型不会重建缺项。

cleanup(item):
    log(...);
    for (off in [0x28,0x2c,0x30,0x34,0x38]) {
        p=load32(item+off);
        if (p!=0) { release_adapter(p); store32(item+off,0); }
    }
```

cmd50 的 fill 只覆盖 `[item,item+0x24)`，不触及 +28 起的指针。调用清理器之前 +0d 清零，+0c 从重新读取的 raw u16+4 的 bit10 写入；随后 `s9=0xfff`，`9368` 跳 `9260`。这里仍有原程序的转换/公共尾部，最终 `92aa` 写 mask、`92e2` 通知；应理解为进入该尾部，不能把 E01 压缩描述当成“cleanup 紧接 callback”的直接调用边。这个补充不改变 E01 结论。

## 原位更新、写宽和通知

| header / subtype | item字段 | 长度 | 赋值mask |
| --- | --- | ---: | ---: |
| 2b010112h | +28 | 20 | 4000h |
| 2b010114h / 1 | +30 | 12 | 8000h |
| 2b010114h / 2 | +34 | 24 | 10000h |
| 2b010114h / 3 | +2c | 24 | 20000h |
| 2b010114h / 6 | +38 | 24 | 40000h |

header 拷贝源为 payload+1、长度8；判断 subtype 的 byte 是 header+7，即 payload+8。真正资源拷贝源是 payload+5。五分支都先 `compare(p,payload+5,n)`，比较为0跳过；不等时才检查缓存的 p，再 copy/log/store mask/notify。Dev 的 `a00a86a8 ef707ab1` 调比较、`86ac` 判结果、`86b2` 判 p，四 subtype 顺序相同；不前移判断，不作异常场景验证。

`a00a8730 23a0fa00` 是 `sw a5,0(s5)`，另四分支设置 a5 后跳回此处，故这里是直接赋值，不能改写为 OR 旧mask。`a00a38f6 8297` 为间接 `jalr a5`，参数由 `38f2 c840` / `38f4 d685` 给出：a0=node+4 的 userdata，a1=此前算出的 item。`a00a38d8 0b502a41` 的编码为 store word zero 到 s4+s2，二者分别是通知前固定数组和 index*424。清零发生于完整 walker 结束，无 retain、深拷贝或嵌套释放。

## 借用转换的数值合同

`a00f4740` 的 word port 先 `(port-1)&0xff` 作借用索引，保存原 port，最后向 dst+0 写低8位。三指针 +28/+2c/+30 依次检查，失败返回0；+34/+38 和 dst 没有这里新增的检查。成功返回1。借用结果不决定 dst 的来源或寿命。

- 每次从 item 重读 +28，将 byte +4,+5,+0b,+0a,+11 分别写到 dst+2,+1,+3,+4,+5；求和截成 u8 写 dst+6。全局 `62fc402c+index+0x3b=62fc4067+index` 在原值0且和非零时写1，此函数不清它。
- 第一次重新读 mask 的 `8000h` 门控制 SOC。p30+8 是 **lhu**；p28+6 为0时 `(raw+99)/100`（原指令为有符号 div，但输入非负），dst+8 为半字，dst+0a半字清0、dst+50 byte清0。否则写 `raw/100`、`(raw%100)/10`，byte+50=1；原余数/除法为 unsigned。
- 接着无条件写 dst+0 port；第二次重新读 `8000h` 才处理 p30+0a。`(u16<<3)/60` 后再除/余60，分别 store16 到 dst+0c/+0e。不能省略这次重读或把门合并。
- 数量 u8和<=4 才生成标签，按 dst+1、+2、+3、+5 的数量依次写类型1、2、3、6。每条标签偏移 `+1c+16*j / +1d+16*j`；单条 ordinal0，多条 ordinal1起。dst+4 参与总数，却无单独生成循环；不补齐第五类。
- 最后重新读 `20000h` 门。成立才清 dst+1e/+2e/+3e/+4e。p2c 的 u16+2 高/低 nibble 作 start/end；start1/end0 把 end改1。输出从 dst+16*start 起，比较 start 的低8位，只更新 `(u8)(start-1)<4` 的槽；其他槽也递增输入序号和输出游标。
- 每条输入从重读的 p2c+4*j 取 `kind=bits11..8(u16+6)`；输出 byte+0=(kind!=0)，kind3写 byte+1=0、kind4写1，其他值保留旧byte+1。`v=(u16+4+50)/100` 是原有符号div，非负输入；`c=(u8+6+1)>>1` 是原算术右移，但该范围内等于非负右移。半字输出+4/+6为v的除余10，+8/+a为c的除余10，+2为`(v*c+50)/100`；byte+e=1。日志支持电压/电流/功率命名，不独立认证协议单位。

这组业务 store 的基址为 dst（后段游标仍由 dst 加偏移产生）或已列全局字节；资源指针仅作为 load 基址，没有写入 dst。因此“item 持有，转换借用，dst 获得数值”的所有权判断成立。不能据此声明真实 caller 与同步通知之间已连成直接调用链。
