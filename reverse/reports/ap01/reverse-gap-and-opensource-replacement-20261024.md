# AP01 逆向成果、开源替代与剩余缺口评估

日期：2026-10-24。盘点基线：`5bbc331ab429fb76e956e50b8081c56f8d278b11`；目标为 `1.0.2_0041`，0031 只作对照。本文采用本次要求：**公共能力允许采用功能等价的开源实现，不要求与 ROM 原实现或版本完全相同。**

## 1. 结论：还缺多少

现有成果已经足以支撑应用层重建；主要缺口转向真实设备接入、专有协议和板级适配。公共库内部不必继续逐函数还原。按本文为规划划分的 **22 个能力包**：

| 分类 | 数量 | 具体含义 |
| --- | ---: | --- |
| 已有开源实现，可停止追原实现 | 8 | 系统、GUI、事件循环、文件系统、分配器、TLS/基础算法、JSON、图片解码；仍有配置、移植和测试工作 |
| 已有行为恢复及 SIM 重建验收 | 3 | 应用页面交互、时间日历、设置界面/宿主保存；实机后端另计 |
| 已部分逆向，仍有专有接入缺口 | 9 | 底座/模式、状态生命周期、天气、原配置兼容、输入/蜂鸣/工厂、显示板级、OTA/启动、MiIO、MiBLE |
| 尚无完整内部实现，替代未落实 | 2 | 无线底层闭源边界、底座 MCU 内部程序 |
| 合计 | 22 | 是工作包划分，不是 ROM 函数数量或等量工作量 |

**因此，当前可明确列出的剩余专有/硬件缺口为 11 包：9 包部分恢复，2 包内部或替代仍未落实。** 另有 8 包开源集成工作，不能把“有源码可用”写成“已移植完成”。11 包是已知功能范围的清单，不是穷尽全 ROM 的证明；来源未决代码可能引出额外适配。

不能据此写成“完成 50%”或“还缺 50%”：GUI 库与米家认证的难度不同，SIM 也不是实机。现有资料不支持可信的总工期、剩余源码行数或全 ROM 完成百分比。旧报告估算的 1.8–5.1 万行业务实现是整个应用层量级，**不能当成剩余工作量**。

## 2. 计算依据与统计边界

### 函数账本

重新读取[首轮机器账本](../../analysis/whole-rom-coverage-0041-20261023-round1.json)的 summary，得到：

```text
6487 个枚举节点 = 797 个仅有开源路径候选
                 + 293 个私有/混合候选
                 + 5396 个来源未决
                 + 1 个外部边界
```

来源未决占模型节点的 `5396 / 6487 = 83.18%`，只表示**来源归属未决比例**，不表示未逆向比例；797 个也不是可以直接删除的函数。局部合同、父级审阅和后续复核存在重叠，没有统一更新后的逐函数完成分母，不能累加报告数或检查项数算完成率。首轮完整私有认证/开源排除均为 0 是当时严格认证口径，并不等于没有恢复成果。

本次放宽的是**替代方案的选择标准**，不是修改历史证据：无需证明 LVGL 原厂版本相同，便可选择用 LVGL 重建 GUI；但不能据此将 797 或 5396 个函数批量改标为已完成。详见[全 ROM 范围](whole-rom-0041.md)与[私有覆盖](private-coverage-0041.md)。

## 4. 开源内容与可替代方案：8 包

“来源线索”和“可替代”分别列账。以下上游于本次在线核对；源码可用不保证直接适配 AP01。版本可选可维护且满足功能的版本，移植时固定提交。

| 编号 | 能力与开源选择 | 原 ROM 的识别依据 | 新实现还需做什么 |
| --- | --- | --- | --- |
| O1 | RTOS/POSIX/系统服务：[NuttX](https://github.com/apache/nuttx)，配套 [apps](https://github.com/apache/nuttx-apps) | 启动表、路径、任务及接口证据；精确原厂版本未知 | AP01 板级、内存布局、任务/驱动配置；不必还原调度器全部机器码 |
| O2 | GUI/控件/动画/缓存：[LVGL](https://github.com/lvgl/lvgl) | 大量 LVGL 路径与局部调用合同，SIM 已用 9.2.1 | 页面接线、输入/显示适配；厂商控件按行为重建，内部布局可自定义 |
| O3 | 异步循环/timer/poll：[openvela libuv](https://github.com/open-vela/apps_system_libuv) | ROM 有 NuttX libuv 适配路径；普通 libuv 检出不含该适配文件 | 对接线程、poll、关闭取消；新代码统一采用选定版本 API/所有权 |
| O4 | 文件系统：[littlefs](https://github.com/littlefs-project/littlefs)，或所选系统原生存储 | ROM 有 littlefs 路径；另有 FatFs 线索但来源未定 | Flash 几何、分区及读写驱动；原配置兼容另计，不能靠换文件系统自动获得 |
| O5 | 堆/分配：[TLSF](https://github.com/mattconte/tlsf) 或 NuttX 分配器 | ROM 有 tlsf 路径 | 按实际 RAM/PSRAM、DMA 可访问性与对齐需求配置；不必复刻 allocator 私有结构 |
| O6 | TLS 与基础密码算法：[Mbed TLS](https://github.com/Mbed-TLS/mbedtls) | mbedtls 日志，摘要另有 MD5 算法静态识别；不能据算法确认原库 | 网络/时间/随机源与协议参数接入；通用算法不能替代米家设备端身份和完整业务协议 |
| O7 | JSON：[cJSON](https://github.com/DaveGamble/cJSON) 等 | 原 ROM 的具体 JSON 库来源未确认；实验载荷还使用过 ArduinoJson | 自定义模型用公开 API 解析；此项按功能替代，不宣称原 ROM 使用 cJSON |
| O8 | PNG/GIF：采用 [LVGL 的解码集成](https://lvgl.io/docs/open/main-modules/images/decoders)，配合 [LodePNG](https://github.com/lvandeve/lodepng)/[gifdec](https://github.com/lecram/gifdec) | ROM 有 LVGL lodepng/gifdec 路径；已有资源清单 | 资源路径、色彩/内存预算、帧调度；不必继续追原 formatter、copy 与缓存内部实现 |

本机同父目录已确认存在 `nuttx`、`nuttx-apps`、`lvgl`、`libuv-openvela`、`littlefs`、`tlsf`、`mbedtls`、`zephyr`、`lodepng`、`gifdec`、`cJSON`、`bouffalo_sdk`。历史提交身份见[来源机器记录](../../analysis/opensource-audit-20261024.json)；本次只确认目录存在，没有重新认证这些检出的内容、状态或构建结果。

**部分开放的 SDK 不算第 9 个完整解决包。** [Bouffalo SDK](https://github.com/bouffalolab/bouffalo_sdk) 提供芯片支持、外设代码及示例，可用于 UART/GPIO/PWM/DMA/Flash 的适配参考；[Zephyr](https://github.com/zephyrproject-rtos/zephyr) 可作蓝牙公共层候选。但芯片公共驱动、无线二进制依赖、AP01 原厂 RTOS 接口和板级接线需分开审计，不能把整个 Wi-Fi/BLE 栈记为开源已解决。

[python-miio](https://github.com/rytilahti/python-miio) 是控制小米设备的客户端库，可作工具和协议参考；它不能直接替代 AP01 的嵌入式设备端 MiIO/MiBLE、绑定与云服务。现有材料尚未落实一个可以直接替换整套 AP01 米家设备端的开源方案。

原厂图像/字体可以按本项目证据用于行为重建，但它们是**已提取的厂商资源，不是开源代码**；也可以另换自有资源。归属边界见 [NOTICE](../../../NOTICE.md)。

这 11 包互按下述责任范围分账；库内部工作归 O1–O8，不重复计入。

| 编号/状态 | 已有基础 | 尚缺的结果 | 开源可替代到哪里/何时可停止追原实现 |
| --- | --- | --- | --- |

| G3 天气服务：部分 | 请求/位置/数据/订阅及页面合同 | 可用数据源、字段映射、调度重试/缓存策略、所有资源归还 | TLS/JSON可直接替换，也可更换天气服务；原服务 URL/token 的逐字一致性不再必需，天气功能仍需接通 |
| G4 原配置兼容：部分 | 普通 namespace/key 后端、部分 CRC/payload、亮度/蜂鸣/地点与设置字段 | 要保留的旧配置读入/迁移、普通 setter 接线、实际持久读回 | 全新程序可用新格式，放弃旧格式兼容即可减少逆向；若与原后台共享配置，仍需守原合同。不能再笼统称所有存储格式未知 |
| G5 输入/空闲/蜂鸣/工厂：部分 | 旋钮业务、唤醒/长按/idle、PWM与背光、灯效/门控 | 实际输入驱动、蜂鸣正常停机/等待关系、工厂模式完整退出及必要硬件时序 | 公共驱动+自定义状态机可替代；保留外观与必要交互即可，不必复制原线程结构 |
| G6 显示与板级外设：部分 | 刷新/poll/事件、fb 文件及像素/PWM 来源局部合同 | LCD/帧缓冲/DMA 实际刷新完成、引脚/面板时序、内存与缓存一致性 | LVGL解决上层；SDK解决部分驱动参考。AP01 板级与物理显示仍须实现/验证 |
| G7 AP01 启动/OTA/恢复：部分 | 镜像准入、分区、加载/打包与有限 QEMU 实验 | 可启动的新固件、更新提交/重启、Boot2/回滚/掉电恢复的可信边界 | 可保留原启动器或换应用更新实现，但镜像/分区/硬件接口必须兼容；底座 MCU 内部另归 G11 |

| G9 MiBLE 绑定/传输：部分 | 传输、计数、认证等局部合同 | 完整设备端绑定状态、传输/错误/重连及真实链路验证 | 通用 BLE host 不等于米家业务；若主动改成本地独立产品，可移出需求，但不是逆向完成 |
| G10 无线底层边界：未落实 | RWNX/LwIP、supplicant、蓝牙 host 等来源线索，SDK 可查 | AP01 可用的驱动/固件组合、二进制依赖边界与 RTOS 适配 | 接受继续使用原厂二进制可缩减为接口适配；若要求全部源码开放，目前无法认定已解决 |
| G11 三份底座 MCU 内部：未完成 | 共 141,878 B 封装、项目流与更新消费边界 | 内部架构/格式/函数、功率控制/保护/升级后行为 | 保留原底座固件时可作为黑盒，仅完成 G1；若要求连底座也从源码重建，仍是独立大缺口，未找到已证实可直接替代的开源实现 |

G2、G5、G8 中的退出/持有问题是原逻辑解释与新实现正确性两件事。新实现可用清晰的公开库寿命规则解决，不要求为了迁就旧对象布局继续追到每个 libc helper。

### 最新专项哪些可以停止深挖

- [A77](reader-driver-format-engine-review-a77-0041-20261024.md)只接受 format 引擎已交付片段，`%s` 取参/输出仍未闭；[A81](reader-driver-format-copy-review-a81-0041-20261024.md)只接受 n=1 copy 的有限域。**完整重建时，使用选定 libc/LVGL/文件系统可绕开这部分原实现恢复**，不再把完整 printf/memcpy 当必要业务缺口。
- [F33](miio-loop-exit-review-f33-0041-20261024.md)接受同 M 的退出接线和创建失败 caller，但不证明实际 quit、queued I 排空及最终 free。若继续调用原厂 MiIO 对象，该边界仍需处理；若全换事件层，可自定义退出合同，仍需验证真实米家功能。
- 旧 J05 的 poll 取消种子已有后继 [G19/G20](pogo-poll-cancel-backend-g19-0041-20261024.md)，随后有 [G21](pogo-poll-submit-g21-0041-20261024.md)、[G23](pogo-poll-ring-consume-g23-0041-20261024.md)、[G25](pogo-poll-op3-g25-0041-20261024.md)、[G27](pogo-poll-error-slot-g27-0041-20261024.md)。不能将旧盘点中“尚待研究”重新算成全部没有恢复；仍不由局部静态合同推出实际取消或硬件停机成功。

## 6. 采用哪种目标，会改变剩余工作

| 目标 | 仍必须完成 | 可从“必须逆向”移出的内容 |
| --- | --- | --- |
| 保留原后台、注入/替换应用 | 应用所调用的原 ABI/对象寿命、显示/输入交接、底座与状态接口、打包启动；原服务继续沿用 | 不接触的库和后台内部实现；原底座 MCU 内部 |
| 自建 AP01 固件，保留原底座，保留米家 | O1–O8 集成及 G1–G10 的必要接入/验证；米家仍为明显专有缺口 | 原库精确来源/版本、原 formatter/copy/cache 的逐函数恢复；G11 可保留黑盒 |
| 自建本地独立固件，保留底座，允许更换天气/联网方案 | 底座协议、显示输入、状态、持久化、启动更新及选定联网方案 | 米家特有 G8/G9 与原天气服务兼容；若无蓝牙需求可缩减相关无线范围；这属于需求裁剪 |
| AP01 与底座 MCU 全源码重建 | 所有必要接入、无线可用方案与 G11 内部功能 | 公共库仍可复用，但目前没有全源码闭环结论 |

本次没有替用户删除米家、更新或底座功能；上述方案只说明可选范围。没有证据时不估算各方案节省的百分比。

## 7. 建议后续顺序与验收

1. 先固定“保留哪些原后台/底座组件”。这决定哪些原 ABI 必须继续恢复、哪些对象内部可以彻底替换。
2. 公共组件以现有源码/SIM 为起点集成，停止以准确匹配原库为通行条件；对原 ROM 未改用的代码不做完成认证。
3. 优先实现真实显示/输入、底座最小正常往返、模式状态通知与持久读回，使已有 UI 接到真实后端。每个工作包记录入口、输出、超时/失败/关闭和验证层级。
4. 米家/无线与启动恢复分别推进，避免把 GUI 可运行当作网络和更新已完成。底座 MCU 保留与否单独决策。
5. 完成判据应是所选功能在目标硬件上经过可复验验证；静态合同、SIM、QEMU、实机四种证据分别保留。
