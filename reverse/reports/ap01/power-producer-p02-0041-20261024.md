## 真正新增

### 输入与对象身份

入口 `0xa00a8582(cmd word,len word,payload*)` 在 `85a0/85a4/85a8` 构造栈descriptor `{u8 cmd,u8 len,pointer@4}`；`85d4/85d8` 以cmd0x50进入 `8b72`。

`8b76..8b8c`读取 `u8 count@0x62fcb01c`，传 `n=(count<<3)&0xf8`、`dst=load32(0x62fcb2d0)` 和descriptor给固定长度更新helper；**不检查helper返回**后继续。raw通知在业务项处理之前；这不证明另一响应或另一订阅回调的真实到达顺序。后续原有工厂显示分支不纳入本题；正常业务入口 `8bac` 重读 `T=load32(0x62fcb2cc)`，T为空则到既有查询推进，不产生本题item/total事件。

`8bb8`缓存当时raw起点R；每轮 `8bcc/8bd0` 重读当前全局T及u8 T.count，以signed BLT比较word索引k。若继续，`91c6..91dc` 从该轮T读取数组A，缓存 `I=A+k*424`；记录 `R` 每轮在 `9380` 加8。T.count和raw count是不同读点，本片段没有将两者验证为恒等。以下“同项”关系以相应读点确实仍指向同一实例为条件。

普通值helper `0xa00a3904(a0=index word,a1=R*)` **重新读全局T**；T空返回0，否则重新从T+0取A并算J=A+index*424，没有本地count检查。它不直接复用caller缓存I。因此不能把caller的I、helper的J、通知器重新取得的项无条件折叠成一个稳定对象。

### 普通值：变化功率位不要求功率数值本身不同

`0xa00a3904` 正常合同如下，原序/宽度保留，伪代码不是原源码：

```c
if (current_global_T == NULL) return 0;
J = load32(current_global_T+0) + index*424;
u32 changed = 0;
u16 v = (u16)((load_u16(R+0)+50) / 100);
if (load_u16(J+4) != v) { store16(J+4,v); changed=5; }
u16 c = (u16)((load_u16(R+2)+50) / 100);
if (load_u16(J+6) != c) { store16(J+6,c); changed |= 6; }
if (changed != 0) {
    // 重新读取两个缓存字段；RV32 mul/add，signed div，最后SH低16。
    store16(J+8, div_s32(mul32(load_u16(J+4),load_u16(J+6))+5,10));
}
return changed;
```

`392a/3930/3934/393c/3944/3948` 对应R+0→J+4及返回位5；`394a..396a` 对应R+2→J+6及OR6；`396e..3982` 重读两半字再派生J+8。正常由上述raw换算得到的v/c为0..655，乘法不会越过signed32范围；本报告仍保留机器宽度，不给任意预置缓存做额外保证。变化位为V=1、C=2、派生P=4；电压或电流任一变化都会置4并重写功率，即使舍入后的功率刚好等于旧值。两者都相等则不重算/比较功率。

此处只有原数值算式。日志/已有消费者支持V/C/功率命名；不能据此把raw wire值直接标为mV/mA、W或额外倍率。应用若复刻显示应沿已证消费者比例。

### 同一记录的状态、活动与附加值

每轮 `s9=0`，先处理R+4，再决定是否调用普通值helper，后接附加值、历史和发布：

| `bit10(u16 R+4) != u8 I+0xc` | 先日志，再**重读R+4**提bit10写I+0xc，s9=0x10。不能把日志前后的读合并。分析日志名AnXin_Mode，不推断硬件功能 |
| `(u16 R+4 & 0x6000)==0x6000` | `u16[0x62fcb50a] |= 1<<k`，半字截断；本路径未见清除，不把它当本题普通mask或已知告警名 |
| `I+0xd==0 && (status&3)==3` | 先写I+0xd=1，再helper(index&0xff,R)，s9 OR helper返回 OR0x20 |
| `I+0xd==0 && low2!=3` | 若status bit0且 `(u8 I+0x24 &0x30)==0x10`，仅R+0同样舍入更新I+4并OR1；**不更新I+6/I+8，也不置4** |

### 逐项通知后再计算总量

每项完成上述处理后：

1. **在历史/通知之前**，若s9&4非零，设置本次total_changes=1；它是“本次有项需要重算总量”的本地标志，不读取或OR旧T.mask。
2. `9298..92a0` 以caller缓存I+8的LHU调用历史(I+0x3c,value)。返回非零，s9 OR0x400；若历史返回0且s9==0，本项跳过发布。
3. `92aa` **直接赋word s9到caller缓存A+k*424首word**，不是OR旧I.mask。日志后 `92e2` 同步通知(index&0xff)。通知器自身重读全局T，借用/清mask沿E02；记录资源仍属生产方。
4. 回调返回才index+1、R+8、回到全局T/count重读；下一项可以见到回调后的当前全局。不能把整个cmd50描述成先写完全部项、再集中通知的原子批次。

循环最后一次边界读取得到的T/count用于下面求和；只有total_changes!=0才先SH0到该T+4，逐项读取其当时数组的u16 I+8，加到累加值并**每步SH低16**回T+4。不是直接把raw功率字段相加，也没有饱和或u32持久总值；结果为sum mod65536。求和发生于全部逐项回调之后，不保证等同通知前缓存的各项数值。

随后 `8c10` **重新读全局T**，LHU T+4、调用历史(T+0xe,value)。若历史返回非零，total_changes OR0x400。历史返回0且total_changes==0则跳过总通知；否则 `8c36` **直接SH total_changes到当前T+0xc**，日志，再 `8c52` 同步总通知。总通知walk每轮重读T并在末尾清当时T.mask，不能据此保证事件mask始终归同一实例。

因此cmd50总事件局部只有功率1和历史0x400（可组合0x401）；item位和total位是两个域。即使raw不变，历史helper仍调用；其历史结果可以产生0x400。相反，只变化I+0xc/+0xa等而没有4且历史返回0时，item会通知、total不会。原routine末进入既有 `0xa0191746` 查询推进；没有为运输错误/超时/取消新建返回码。

### 面向应用的接口（重建设计选择）

同步item回调内复制 `{index,mask,u16+4,+6,+8,+0xa,u8+0xc,+0xd}`，按事件位更新应用自有值和“是否曾收到”标记；不要以mask非零永久代表有效性，也不要只订阅total就预期收到所有状态。同步total回调内复制 `{u16 T+4,u16 T+0xc}`及确实需要的当前字段。回调外持有复制值；资源/item/T指针仍为借用。

若需要一致全量视图，重建程序可以串行化接收与捕获，并给自有对象加代际/序号；这些是新设计，ROM未证有锁、原子快照或跨响应实例保证。复刻原厂时保留两种mask直接赋值、逐项先通知、后总求和及各重读点；不把它们替换成持续OR累计或先收齐再通知。
