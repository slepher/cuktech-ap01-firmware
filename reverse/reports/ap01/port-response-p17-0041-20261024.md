分析伪代码，非原厂源码，只投影本题正常分支：

```c
// 前置：正常parser已经匹配活动cmd，当前handler确为ordinary。
void response_63_or_65(uint32_t cmd, uint32_t len, const uint8_t *payload) {
    // cmd63/65到达共享0x61..0x68分支。
    ack_copy_a01ad024((void *)0x62fcb50d, 1, payload);

```

`len`只按byte存栈，本题实际路线没有按len决定copy长度；正常可用合同要求payload首byte可读。这里只描述正常回应，不据此生成短输入/异常回放或安全结论。`0xa01ad036`明确SB零至`0x62fcb2f0`，发生在`0xa01ad03a/3e`调用既有copy之前；不能把它改成“业务成功才清state”。

### 可观察的是共享回复与后续独立遥测

`0x62fcb50d`为全局1B存储，cmd60及共享61..68路径都会写它。本路线不保存index、请求value、command tag、序号或时间戳，不判断byte是否0；其含义未知，不能命名为“成功码”。稍后其他同路径回复可覆盖该byte。此为已核写入路径的事实；本轮没有穷举其所有reader，不宣称整个固件无法暴露该缓存。

对63/65，从`9cbc`到返回没有调用`0xa0191652`、轮询selector`0xa0191746`、submit、UiIFace分发器或日志结果分支。因此没有本分支同步派生的0x83/0x85事件，也没有本分支发起的立即读回；这个负结论只限该确定路线，不扩成全局没有业务结果或查询能力。

首次handler返回后，parser按B21重读当前handler，再调用`(0x24,0,NULL)`。若此时仍为ordinary，`0xa00a8856..886e`读OTA阶段`0x62fcb2ef`：等1走`0xa00a56d4`，其余尝试`0xa01915bc`。后者仍受transport空闲/槽占用门；如同步执行中state已变，不能缓存刚才的state0当保证。第二次通知没有携带63/65、应答byte或index，可推进任意当前优先槽，不能作为这次控制成功/立即查询的证明。完整parser与队列逻辑沿B21，不在本轮重新恢复。

真实后续查询来源继承P-10：普通timer门满足时selector按表/phase/sent发len0查询，默认快组58、慢组50/51/57/59；正常cmd50响应再按P-R02产生I+0xc/mask0x10和I+0xa/mask8，P-14的同页callback可呈现。控制请求可以在调度链中穿插，但cmd63/65本分支没有重置phase/sent或主动调用selector，也没把随后cmd50与这次请求关联。最近遥测变化能显示观测值，不能证明由本请求造成、量测足够新、持久化或外部物理映射已正确。
