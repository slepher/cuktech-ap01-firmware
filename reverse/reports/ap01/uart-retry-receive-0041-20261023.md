## 重试合同：传输耗尽不代表 OTA 退出

`a00eea08` 的汇编与回放共同支持以下合同，Evidence `ev_021bd54f55bfe7377212f9326e2464036ff50b471caa8365aca7a46812825cf7`：

| RAM | 本轮确认的读写含义 |
| --- | --- |
| `62fcb2f0` | 只有值 2 才推进重试检查 |
| `62fcb2f2` | 等待计数 byte；每次有效调用先加 1，按 8 位回绕 |
| `62fcb4f8` | 等待阈值；递增后的计数小于它时直接返回 |
| `62fcb2f1` | 尝试计数 byte；小于 5 时构帧、尝试写出，再加 1 |
| `62fcb6c0` | 耗尽时读取的当前响应处理函数 |

尝试计数已经达到 5 且等待阈值满足时，helper 先把传输状态置 0，再向非空处理函数发送 `(0x24,0,0)`，最后调用 `a00ee9ce`。这里没有设置 OTA 失败码，也没有直接修改 OTA 阶段 `62fcb2ef`。11 组回放覆盖非等待状态、阈值边界、计数 255 回绕、重发和耗尽；夹具下 OTA 阶段保持原值 3。

因此不能把传输状态 0 写成“OTA 已失败并退出”。实际 `a00a5810` 的 `0x24` 分支只调用 `a01915bc` 尝试消费排队命令；是否有后续超时或断连使 OTA 退出仍需端到端追踪。该局部合同提示存在等待阶段滞留的可能性，尚未证明实机一定停滞。

另一个容易误读的点：helper 的重发分支**没有清零等待计数**。`a00ee9ce` 只在传输状态为 1 的首次发送路径将尝试计数置 1、等待计数置 0。`a01a4ff8` 重建帧、`a00ee96c` 推进部分写的已观察 body 也没有清该等待计数。因此不能将阈值 2/10 简化成“每一次重发都重新等待 2/10 个周期”。耗尽后回调可能改变全局状态，必须按实际执行顺序分析后续调用。

### 调度与连接状态门控

`a00a805a` 是引用名称为 `pogo_pin_timer_cb` 的回调，Evidence `ev_5fd69f489ac24670f4c858f79225e681a50079c28b088bb18e6f7b999de4fa59`。它先按上下文 `+0x190` 的 0..4 五个相位轮转；UART/底座业务位于相位 3，还受上下文 `+0xc5` 非零门控。

- 控制 byte `62fcb50c==1` 时调用重试 helper；等于 3 时仅在子计数 `62fcb51c==0` 调用。
- 子计数遍历 0..10，超过 10 后归零。其他门控条件和相位同样影响 helper 的实际调用间隔。
- 控制值 0 的初始化分支清接收/发送/活动描述符区域，阈值置 2、响应函数置 NULL；发现流程在子计数为 0 时清四个排队槽、恢复普通响应函数并发送 D1。
- `a00a56d4` 进入 OTA 时将控制 byte 置 3、阈值置 10，并切换响应函数；`a00a4708` 退出时恢复阈值 2。

第三轮初始化 dossier `ev_dc0e38b0f382799ea2a8e8ad7f21cefc5998b0767ecf38a58cfdebe8add167c3` 可见 `a008bc64(a00a805a,0x14,context)` 的注册以及 UART poll 回调 `a00a8330` 的注册。本轮记录 period 参数为 20，尚未沿定时器实现验证其时间单位，也不把重试阈值直接换算为毫秒。

## 接收合同：CRC 与声明长度使用了不同边界

`a00a8330` 的 Evidence `ev_6f900403de24d247461a1e302c564c71481c3d43d481acdc83bbb716318e1159` 包含以下可逐指令复查的路径：

1. 解码字节数大于 4 时，CRC 覆盖实际解码字节数减 2；末尾 2 B 用于比对 CRC。
2. CRC 相同、活动传输状态为 2、响应 cmd 与活动 cmd 相同后，读取帧头声明长度 byte `62fcb45a`。
3. `a00a8506..a00a8510` 将这个 byte 加 2，用作 `memcpy(62fcb322,62fcb459,declared_len+2)` 的长度。此局部路径没有将它与实际解码长度对应比较。
4. 复制后置传输状态为 3，以复制后的 cmd/len 派发响应。len 为 0 时 payload 参数为 NULL。

CRC 验证了实际收到的字节，不能自行证明帧头所称的 payload 存在。环形读取区 100 B 和解码追加 helper 的 47 B 计数边界也不能约束这里的 `declared_len+2` 复制长度。

### 原厂指令的有界回放

| 用例 | 实际 payload | 声明长度 | 原厂 memcpy 长度 | 抵达回调时观察 |
| --- | ---: | ---: | ---: | --- |
| 空 payload、长度 0 | 0 B | 0 | 2 B | cmd D0、len 0 |
| 正常单字节状态 | 1 B | 1 | 3 B | cmd D0、len 1 |
| 短帧声明长 payload | 0 B | 255 | 257 B | cmd D0、len 255；相邻 RAM 标记改变 |

三个输入均由宿主生成合法 CRC，且原厂 CRC helper 实际执行一次后通过。第三个用例仅 7 B 的线缆帧即可抵达复制；复制从合成接收区读到未接收的哨兵字节，写入目的区时将 `62fcb420` 的标记从 `0x7e` 改为 `0xa6`。该地址按上一轮合同保存 OTA 失败码。此观察证明在声明夹具条件下存在**缺少长度一致性检查导致的跨区域复制**，不再仅是“需要核查的长度疑点”。

这仍没有证明真实底座可发送该输入、设备现场具有同样前置状态或后续可执行任意代码。回放在响应函数入口停止，没有执行 D0 长度 0 时下游的单字节读取，也没有将这条路径冒称完整攻击链。

接收函数先调用当前响应函数，返回后重新加载 `62fcb6c0` 再发送 `0x24`，所以两次通知不保证使用同一个处理函数。恢复源码或模拟器时应保留这个顺序，不能先缓存一次函数指针然后连续通知。完整回调销毁及并发合同仍未完成。
