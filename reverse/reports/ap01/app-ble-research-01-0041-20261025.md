## 本轮复核或纠正：两个角色的 characteristic 身份不同

**本机 role0 的 characteristic 是 UUID16 选择值，peer role1 的 characteristic 是发现得到的 value handle。不能统一当作实际 ATT handle。**

旧 M03 称本机六个 handle 由注册动态产生，此表述应限定/纠正：gateway 在 `a012b62a` 从应用 characteristic record `+4` 取 UUID16，`a012b62e` 原字 `sh a0,0x1e(s1)` 原样写入应用所谓 handle；`a012b632` 再调用 `a00b4b8e`。之后 arch callback `a0127ec2` 将 `+0x1e` 搬入 `62fd3166..62fd3170`。因此本机 auth=`0x10`、stand_auth=`0x19`，不是从无线注册返回的动态 value handle。

`a00b4b8e..a00b4bc8` 从静态 service `62fc4db8` 的 attr array/count 出发，以0x14 B步长遍历；先读 attr `+0` UUID指针，再要求 UUID type byte=0，比较 UUID `+2` u16 与传入 characteristic，找到返回 attr pointer，否则 NULL。此 lookup 的原字路径已保存。实际 ATT handle 位于下层 attr 自己的 `+0x10`，不应伪造成本机 `0x19`。

peer 侧则继承 `a0125a16` discovery：UUID `0x19` 对应 discovery entry 的 value handle 被保存到 `62fd315c`（相关 CCC另存），gateway 再并入按 conn 查得的 master context。这里的 handle 来自 peer discovery，不应用本机 `0x19` 替换。FE95及UUID身份沿用旧报告；无实机观测。

## 真正新增：双角色提交合同

以下为静态恢复伪代码，非原源码；`int32` 返回由 RV32 `a0` 传递。

| 阶段 | 参数与必要转换 | 返回/边界 |
|---|---|---|
| `a012511c(ctx,seq,role)` | ctx+4 经 `lhu`；临时栈帧长度 `(payload_len+2)&0xff` | role0→`a01905be(char16,frame,len8)`；非零role→`a00b4d56(conn16,char16,frame,len8)`；保留下层返回 |
| `a01251cc(role,ctx,status,missing,count)` | ctx+4 `lhu`，conn `lhu`；普通长度4，missing长度 `(4+2*count)&0xff` | role0同上三参，非零role同上四参；旧 void 类型不成立 |
| `a01905be(characteristic,data,len)` | characteristic用于UUID查 attr；构造24 B清零 notify descriptor，+4 attr指针、+8 data指针、+0xc `u16(len)`；conn对象取自 `62fcc188` | lookup失败 −1；`a00d1b3a(conn*,descriptor)` 返回<0→−7，否则0；不透传下层具体errno |
| `a00b4d56(conn,characteristic,data,len)` | 12 B清零连接查询包，+0 `u16(conn)`；`a018fe44(&query)`；要求+8 byte非零且+4 conn*非NULL | 查询失败 −9；调用 `a00d2be2(conn*,characteristic,data,len,0,0,0)`，返回0→0，任意非0→−1 |

`a01905be` 名称由原件 log string `a06276e4` 的 `mible_gatts_notify_or_indicate` 支持；实际本分支通过 `a00ceaa2` 构造 opcode `0x1b` notification，没有在本路径切换到 indication。`a00b4d56` 名称由 `a0561acc` 的 `mible_gattc_write_without_response` 支持，`a00d2be2` 对 `sign=0` 使用 opcode `0x52`（write command），回调及 user_data 均传0。名称/操作码支持正常用途，不认证库精确版本。

调用点宽度由汇编确认：帧层先将 length截为u8、characteristic/conn以u16零扩展；role0 wrapper自身将len存成u16。role1 wrapper将conn截为u16，characteristic在下层编码为两个字节，len在下层以寄存器值使用。本报告只承诺这两个已观察帧调用的位宽，不将其推广成任意公共调用者的完整范围检查。

### 缓冲借用和本地完成边界

1. **role0**：`a0190626..a019062e` 将 attr/data/len写到临时 descriptor。`+0x10/+0x14` 保持清零，因此没有本帧的 completion callback/user_data。`a00d1b3a` 在 conn非NULL路径调用 `a00ceaa2`；后者在 `a00ceb26..a00ceb3c` 从 descriptor `+8/+0xc` 读取源和长度，先取得独立 packet空间，再调用公共 copy `a000589c`，随后才提交 packet（`a00ceb48`）。正常非NULL连接路径的临时 frame/descriptor在该同步调用返回后即可结束借用。下层 conn=NULL 分支存在遍历路径，但本轮没有把其广播/订阅行为恢复为完整合同，也不据此宣称所有NULL分支的借用均已验。
2. **role1**：`a00d2c74..a00d2c90` 分配 packet、写两字节characteristic，再用 `a0190248(packet,len,data,0)` append；返回 copied_len不等于len时释放packet并返回 −12；等于len才在 `a00d2cdc` 交给下层发送。`a0190296` 调用 append/copy边界 `a01adb2c`，其 `a01adb4a..a01adb4e` 直接落到公共 copy `a000589c`。源指针用于同步复制，不作为completion user_data保留。临时 frame 在 append和提交调用返回后可结束借用。`a0190248` 内含厂商指令，通用Capstone不能独立闭合所有分片分支；本报告不展开公共 buffer库，也不宣称已完整恢复其内部算法。
3. wrapper成功0只表示本地提交API未报错。role0清零callback，role1传NULL callback，均没有为此帧建立可等待的ATT异步完成槽。ATT write command本身也没有本路径的 response完成合同。**submit成功不能写成peer已收到**，可靠层之后收到的协议 ACK 仍是独立事件；worker callback亦不是无线送达证明。
4. 这只结束临时帧借用。上层 transfer原始 payload依然必须保留至U04 owner completion/reset/disconnect规则允许回收；不因本轮copy证据而提前释放整个transfer。

### 必要 ingress：继承并核对同 characteristic，连接身份仍有限定

本机 GATTS `a01258e4` event `0x40` 读取 characteristic标识 `+4`、data指针`+8`、length u8 `+0xc`，同步复制后经 `a012087a(0x100,...)` 进入固定消息队列。gateway 在 `a012d37a..a012d3be` 将标识与本机 stand_auth `62fd3170` 比较，长度再次`&0xff`，以 queue-local payload 调用 `a0125280(62fca770,data,len)`。此分支没有新增独立conn匹配；不能因 characteristic相等就宣称多连接隔离或与 `62fcc188` 必为同一对象。

peer notification：`a0125a16` event`0x83` 拷贝至多20 B，并将conn/characteristic一同入队`0x202`。gateway先调用 `a0125092(conn16)` 查四个50 B master context；standard模式才比较该context `+0x18` 的stand_auth handle，再向 `a0125280(62fd3384,queue_data,len)` 交付。该有限路由已由旧根恢复，本轮不重做解析器或可靠状态机。

GATTC event`0x82` 的`0x201`完成事件是另一条已存路径；不能把它套到本轮无响应写/NULL callback调用上。GATTS events`0x41..0x43` 在现有callback仅记录，也没有驱动本帧完成。队列及gateway复制使到`a0125280`的数据无需继续借用原BLE callback源缓冲；队列失败返回及长度上界问题维持旧M02边界，不开展异常输入研究。
